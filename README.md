# multiengine-browser

A browser where each tab can run on a different rendering engine — Blink (via CEF), Servo, WebKit (via WebKitGTK), or Blink again (via Microsoft Edge WebView2) — and the engine backing a tab can be swapped live without closing it.

Status: M0–M5 complete — single-engine tabs on Servo/CEF/WebKit, live engine swap, a real chrome, crash recovery, and multiple tabs shown as a force-directed graph (peek to preview, click to focus), all verified end-to-end. Full milestone plan: `C:\Users\Winston Li\.claude\plans\stateless-napping-sunset.md`. **M6 (WebView2, off-plan):** a fourth engine, native Windows API rather than a same-machine child of a separate SDK/runtime checkout — frame capture (`Windows.Graphics.Capture`), navigation, favicon, zoom, click/scroll/text-entry input (via `ExecuteScript`, not OS-level injection — see Known limitations), taskbar-hiding for its off-screen host window, and popup interception (`target=_blank`/`window.open()`/ctrl+click) are all implemented and verified live.

## Architecture

```
browser-ui            winit + wgpu compositor, process manager, swap logic
engine-host-servo     Servo, same-machine child process (named pipe + shared memory)
engine-host-cef       CEF (Blink), same-machine child process (named pipe + shared memory)
engine-host-webkit    WebKitGTK, hosted inside WSL2 (TCP transport, no shared memory across the VM boundary)
engine-host-webview2  Microsoft Edge WebView2 (Blink), same-machine child process (named pipe + shared memory)
ipc-protocol          shared message types + both transports
```

Only `engine-host-webkit` is Linux-only (no Windows WebKit embedding exists); everything else builds natively on Windows.

## Prerequisites

- **Rust** (stable), via rustup.
- **Visual Studio 2022, 17.14 or newer.** Older toolsets are missing STL symbols that Servo's build needs — this is a hard requirement, not a suggestion.
- **A real `ninja.exe`** on PATH (`scoop install ninja`), for CEF's build script.
  - If a Chromium `depot_tools` checkout is also on your PATH, **exclude it** for this project's builds — its extensionless `ninja` shell script shadows the real `ninja.exe` and breaks the CEF build. See the "Building" commands below, which strip it automatically.
- **WebView2 Runtime** — preinstalled on Windows 10 1803+/Windows 11; if missing, `engine-host-webview2` fails to create its environment at startup (respawns in a crash loop rather than silently doing nothing). Check via: `reg query "HKLM\SOFTWARE\WOW6432Node\Microsoft\EdgeUpdate\Clients\{F3017226-FE2A-4295-8BDF-00C3A9A7E4C5}" /v pv`.
- **WSL2, distro `Ubuntu`**, with:
  ```bash
  sudo apt-get install -y libwebkit2gtk-4.1-dev libgtk-3-dev xvfb build-essential
  ```
  (Rust/cargo must also be installed inside that WSL2 distro, separately from the Windows-side toolchain.)

## Building

**Windows-side crates** (`browser-ui`, `engine-host-servo`, `engine-host-cef`, `engine-host-webview2`) — from a regular shell at the repo root:

```bash
PATH=$(echo "$PATH" | tr ':' '\n' | grep -v -F "depot_tools" | tr '\n' ':') cargo build -p browser-ui -p engine-host-servo -p engine-host-cef -p engine-host-webview2
```

The `PATH` filtering is only needed if `depot_tools` is on your PATH; harmless otherwise.

**WebKit engine-host** — built *inside* WSL2, into its own target directory (it can't share `target/` with the Windows build — different OS, different toolchain):

```bash
wsl.exe -d Ubuntu -- bash -c 'cd "/mnt/c/Users/<you>/Documents/GitHub/multiengine-browser" && CARGO_TARGET_DIR=target-linux cargo build -p engine-host-webkit'
```

Adjust the path for wherever this repo actually lives on your machine (WSL2 sees your Windows drives under `/mnt/c/...`).

### Runtime-file placement (required after every build)

Cargo doesn't do this itself — see the `TODO` in `crates/browser-ui/src/process_manager.rs`'s `engine_binary_path`. Both CEF and Servo need extra files placed next to their binaries after each build, because they'd otherwise collide (both ship an ANGLE `libEGL.dll`/`libGLESv2.dll` under the same filenames, and Windows resolves an implicit DLL dependency from the loading EXE's own directory first — whichever copy landed there last silently wins for *both* engines).

`engine-host-webview2` doesn't need this: WebView2Loader is a single small loader, statically linked by the `webview2-com` crate (or at worst one lone DLL) — none of the ANGLE-style same-filename collision the other two have.

Run this after every build that touches `engine-host-servo` or `engine-host-cef`:
```bash
bash scripts/sync-runtime-deps.sh
```
It finds Servo's ANGLE DLLs and CEF's runtime under `target/debug/build/{mozangle,cef-dll-sys}-*/`, `cmp`s each against the copy already in place, and only recopies what's actually stale (safe to run any time — a no-op if nothing changed). Not a build.rs: a build script only sees its own crate's `OUT_DIR`, not a sibling crate's, and there's no reliable cross-crate coordination here without those upstream crates cooperating (they don't) — a plain script is simpler and more honest than fighting Cargo's model.

Why this needs a script at all rather than a one-time manual copy: Cargo has regenerated the `mozangle-<hash>`/`cef-dll-sys-<hash>` fingerprint directory these live under even on a rebuild that touched neither `Cargo.toml` nor `Cargo.lock`, leaving a stale copy in place that keeps working right up until it silently doesn't (Servo: panics with `egl function was not loaded`; CEF: silently runs stale code). The script picks the candidate whose own output *file* has the newest mtime, not the containing directory's — a build touches every candidate directory's own fingerprint bookkeeping on every invocation regardless of whether it actually recompiled that crate, which can leave several near-identical timestamps and make directory-mtime-based "newest" ambiguous.

A rebuild also tends to leave the *previous* hash's directory behind alongside the new one (Cargo doesn't clean up an old fingerprint just because it's no longer used) — these accumulate across sessions and are a repeat cause of this project filling the disk. Safe to prune anything under `target/debug/build/{mozangle,cef-dll-sys}-*` except whichever one `scripts/sync-runtime-deps.sh` just used — re-run the script afterward to confirm nothing needed recopying. Getting this wrong (deleting the wrong one) just means the next build regenerates whatever's missing, not silent breakage — but it's wasted rebuild time.

## Running

```bash
target/debug/browser-ui.exe
```

Starts on **Graph view**, with one root tab (Servo, loading `https://example.com`) already spawned and focused — click its node to enter Tab view. The graph is the primary view for managing multiple tabs:

- **Graph view**: every tab is a node (its last frame as a downscaled thumbnail, favicon, title, current engine) connected by an edge to the tab it was opened from. Hover a node to peek an enlarged preview without changing focus; click a node to focus it (switches to Tab view); drag a node to reposition it (a force-directed layout otherwise keeps nodes spread out and settles on its own — edges settle to a rest length of 320 points, up from 180, so sibling nodes no longer crowd/overlap each other at equilibrium, and separation of a fresh overlap (e.g. several tabs opened in a quick burst) now happens within well under a second rather than visibly lingering for several seconds); the small "x" at a node's corner closes that tab, reparenting its children to its own parent. "+ New Tab" opens a child of whichever tab is currently focused (or a new root if none is). Drag empty background to pan, scroll to zoom (centered on the cursor); "Reset View" returns to the default framing, now at a closer-in default zoom (the scene's default world-space extent shrunk from 1600×1100 to 900×620) so nodes read larger on first open instead of needing an immediate manual zoom-in.

Switching between Graph and Tab view (clicking a node, or the "Graph"/Escape button) animates as a 220ms shrink/expand: the transitioning tab's live content morphs between full-window size (Tab view) and its graph node's thumbnail-sized rect (Graph view), smoothstep-eased, rather than cutting instantly. This reuses the exact same world→screen transform the graph's own `Scene` container uses to place nodes (replicated by hand in `App::graph_world_to_screen_transform`, matching egui 0.36's internal `fit_to_rect_in_scene` formula — not exposed publicly, so not a dependency, just the same math) so the animated rect lands exactly on the real node position, not an approximation. During the animation the app stays logically in Graph view (chrome, physics tick, node layout all keep running underneath) with only the one transitioning tab's content quad drawn at an interpolated viewport rect, layered *on top of* the graph (not underneath it) so the shrinking/expanding content is never hidden behind other nodes/edges as it animates.
- **Tab view**: today's chrome for whichever tab is focused — address bar (type a URL, press Enter), back/forward, an engine-picker dropdown (swaps the tab live between Servo/CEF/WebKit/WebView2), favicon next to the title. The "Graph" button (or Escape) returns to the graph.

A gear icon (in either view's toolbar) opens **Settings** — default search engine (DuckDuckGo/Google/Bing; only where a search actually goes, suggestions always come from DuckDuckGo's own endpoint regardless), default starting engine for new tabs, zoom (a linear multiplier, applies to new tabs and immediately to whichever tab is currently focused — not retroactively to other already-open tabs), and home page. Every control saves immediately on change (no separate "Save" step) to `%APPDATA%\multiengine-browser\settings.json`; a missing or corrupt file just falls back to defaults rather than failing to start. Zoom is implemented on all four engines: Servo (`WebView::set_page_zoom`, a direct linear factor) and CEF (`BrowserHost::set_zoom_level`, log-scale internally — converted via `log_1.2(factor)` so the same setting means the same visual size everywhere) were added along with this settings feature and verified live (visibly larger text at 130%, both engines); WebKit's `set_zoom_level` handler already existed from earlier work and receives the same message the same way — not independently re-verified live, but nothing about it should differ. WebView2 (`ICoreWebView2Controller::SetZoomFactor`, also a direct linear factor) verified live at 150%.

Typing into the address bar shows an autocomplete dropdown below it: matching open tabs first, then DuckDuckGo search-query suggestions (debounced, fetched from DuckDuckGo's own `/ac/` autocomplete endpoint). Click a row to accept it — clicking an open-tab row focuses that tab, clicking a search row navigates to that search. Up/Down move a highlight through the rows (wrapping at both ends); Enter accepts whichever row is highlighted, or falls back to navigating the typed text directly if none is. Non-URL input (no scheme, no dot, or contains a space) is treated as a search query on plain Enter too, resolved the same way as the dropdown's own suggestions. Escape dismisses the dropdown without leaving Tab view; a second Escape (or with no dropdown showing) returns to Graph view as usual.

Keyboard shortcuts work in either view: `Ctrl+T` opens a new tab (same as "+ New Tab" — a child of whichever tab is focused, staying put rather than auto-focusing), `Ctrl+Shift+T` reopens the single most recently closed tab (its original url/engine, falling back to a new root if its original parent was itself closed since), `Ctrl+W` closes the focused tab, `Ctrl+L` focuses the address bar (Tab view only), `Ctrl+F` opens the find-in-page bar (Tab view only), `Ctrl+=`/`Ctrl++`/`Ctrl+-`/`Ctrl+0` zoom in/out/reset (same step, cap, and floor as the settings popup's own +/−/Reset buttons — confirmed live: five `Ctrl++`s took `zoom_factor` from 1.0 to exactly 1.5, visibly larger text), `F12` opens the focused tab's engine's own native DevTools, and `Ctrl+Tab`/`Ctrl+Shift+Tab` cycle focus through open tabs in the order they were opened (this graph-based UI has no tab strip to define a more meaningful order). All are checked via egui's own input polling, consuming the key so it never leaks through to a focused tab's page. `Ctrl+Shift+T` only remembers one tab (not a full stack like some browsers) — confirmed live: closing a tab navigated to a real url and reopening it respawns at that exact url, verified via `session.json` rather than a screenshot (this graph-based UI's node positions are physics-driven, so a fixed click coordinate isn't a reliable way to re-select the respawned node in an automated test).

`F12`'s DevTools is a real, separate OS window the engine manages itself (not part of the tab's own captured/composited content) — confirmed live on CEF and WebView2, each popping up its own real "DevTools - <url>" window. WebKitGTK has the matching API (`WebInspector::show()`) but it's deliberately left as a no-op: this project's WebKit engine-host runs inside an `xvfb-run`-launched X session with no window manager, and a real top-level window shown with nothing to map it pegged the process at ~45% CPU indefinitely in live testing (confirmed: never returned to servicing IPC, had to be force-killed) rather than failing visibly — not safe to ship without adding a window manager to that Xvfb session, a bigger change than this warranted. Servo's embedding API has no DevTools/inspector method at all, same per-engine gap as find-in-page.

`Ctrl+F`'s find bar (top-right of Tab view) searches the focused tab's real page content as you type, via each engine's own native find API — `ICoreWebView2Find`/CEF's `BrowserHost::find`/WebKitGTK's `WebKitFindController` all highlight matches directly in the page and report a live match count; Prev/Next (or Enter/Shift+Enter) step through them, the "Aa" toggle switches case-sensitivity (re-searching immediately, resets to off on a fresh search), Escape or the bar's own close button ends the search. Verified live on CEF and WebView2 (highlighting, match count, active-match tracking, and the case-sensitivity toggle all correct — e.g. searching "banana" against a page with one capitalized "Banana" and two lowercase drops the count from 3 to 2 with the toggle on); WebKit's wiring is written against the same `WebKitFindController` API this project's favicon code already uses successfully, but not build/run-verified this session (WSL2 itself failed to start in this environment — a VM-creation error unrelated to this change). Servo has no find-in-page API in its embedding surface at all — the bar still opens on a Servo tab (confirmed live: no crash, no hang) but never shows a match count, same per-engine gap as popup interception.

Only the focused tab ever actually renders — every other tab's engine-host process stays alive (so its page keeps running, JS timers and all) but stops producing frames until it's focused again; its node just shows the last frame it produced. New tabs are created via "+ New Tab" (or `Ctrl+T`), or automatically as a child node when a page opens one itself (`target=_blank`/`window.open`/ctrl+click) — CEF, WebKit, and WebView2 all intercept and forward these; Servo does not (falls back to its own unhandled-popup default), see Known limitations.

If an engine-host process dies (crashes, or is killed) — focused or not — the tab automatically respawns the same engine at its last-known URL, keeping its place in the graph.

The URL carries over on an engine swap; other state (cookies, scroll position, etc.) does not — a known v1 limitation, not a bug.

The whole tab graph (which tabs, their url/engine/graph position, who opened whom, which tab is focused, which view is active) is saved to `%APPDATA%\multiengine-browser\session.json` on every change that matters (a tab spawns, closes, navigates, or focus/view changes) and restored at the next launch, instead of always starting over at one root tab on the home page. A missing or corrupt session file just falls back to that original single-root-tab startup. Like an engine swap, only the graph's shape is portable across a restart — a restored tab is a fresh navigation to its last known URL, not a resumed one (no cookies/localStorage/scroll position).

Each engine-host writes its own log to `%TEMP%\multiengine-browser-<tab_id>.log`.

## Headless mode (automated testing)

```bash
target/debug/browser-ui.exe --headless
```

Runs the same app, but the window is positioned far off-screen (not `--visible(false)` — a genuinely invisible window's swapchain never successfully acquires a frame on Windows, DWM permanently reports it occluded; an off-screen-but-visible window keeps rendering normally while never overlapping the user's actual screen) and driven entirely by a text-command protocol read from stdin, one command per line, instead of real OS input. This exists so live GUI testing of this app doesn't have to fight Windows' foreground-lock (`SetForegroundWindow` can be silently refused while the user is active on their own machine — see project memory) or contend visually with whatever the user is doing.

Commands:
- `MOUSEMOVE <x> <y>`, `MOUSEDOWN <x> <y> [left|right|middle]`, `MOUSEUP <x> <y> [left|right|middle]`, `CLICK <x> <y> [left|right|middle]` — dispatched as genuine synthetic `winit::event::WindowEvent`s, not a logic bypass, so they exercise real egui hit-testing exactly like real input would.
- `SCROLL <x> <y> <delta_x> <delta_y>`
- `ADDRESSBAR <text>` — sets the address bar's text and focus state directly and recomputes suggestions (headless has no way to synthesize a real click-driven egui focus transfer, since `winit::event::KeyEvent` has no public constructor outside the winit crate — see `debug_control`'s doc comment).
- `ENTER` — navigates using the address bar's current text.
- `ESCAPE` — dismisses the suggestion dropdown, or leaves Tab view for Graph view if none is showing.
- `ARROWDOWN` / `ARROWUP` — moves the address-bar dropdown's highlighted row (wrapping at both ends); a following `ENTER` accepts it.
- `TYPE <text>` — sends each character to the focused tab's page (not the address bar).
- `KEYPAGE <name>` — sends a KeyDown+KeyUp of the named key (`Enter`, `Backspace`, `ArrowLeft`, a single letter/digit, etc.) to the focused tab's page.
- `NEWTAB` / `CLOSETAB` / `FOCUSADDRESS` / `NEXTTAB` / `PREVTAB` — the `Ctrl+T`/`Ctrl+W`/`Ctrl+L`/`Ctrl+Tab`/`Ctrl+Shift+Tab` shortcuts' exact same effect, called directly (same rationale as `TYPE`/`KEYPAGE`: no public way to synthesize a real `Ctrl`-chorded `KeyboardInput`). `FOCUSADDRESS` is the one command among these that isn't instant — it drives a real `egui::Response::request_focus()`, which (immediate-mode) only takes visible effect starting the *next* frame, so it also forces a redraw itself rather than relying on some later, unrelated command to eventually trigger one.
- `SCREENSHOT <path>` — saves the next composited frame (chrome, any open dropdown, and content) as a PNG, read back directly from the GPU rather than `PrintWindow`/`CopyFromScreen` (see project memory's gotchas on GDI-handle exhaustion and foreground-lock unreliability with that approach).
- `RESIZE <width> <height>`
- `SETVISIBLE <true|false>` — sends `SetVisible` directly to the focused tab, bypassing `focus_tab`/`leave_to_graph`'s own visibility changes (which always come bundled with a `Resize`, since Tab vs. Graph view's chrome heights differ). For testing the background-tab suspend/resume path in isolation.
- `QUIT` — exits cleanly. Also sent automatically on stdin EOF, so a driving script that closes its write end doesn't leave the process hanging.

`scripts/headless-smoke-test.sh` is a runnable example (and a real regression smoke test): drives the address-bar autocomplete flow end to end via a bash `coproc` and asserts each screenshot was actually produced and isn't suspiciously small — not full visual-regression testing (there's no state-query debug command yet to assert exact content), but enough to catch a crash or total breakage. Run it after `cargo build -p browser-ui`. Note for anything driving this from Git Bash/MSYS: a `SCREENSHOT` path travels over stdin, not argv, so it's not auto-translated from a POSIX path (`/c/Users/...`) the way a command-line argument to a spawned native exe would be — convert with `cygpath -w` first.

## Known limitations

- Session state (cookies, localStorage, IndexedDB) is not portable across an engine swap — only the URL carries over.
- **Fixed:** spawning a WebKit tab used to be able to freeze the entire app (unresponsive to all input, including headless-mode commands) for anywhere from sub-second to multiple hours. Two root causes, both hit on every WebKit spawn: (1) `ipc-protocol`'s `accept_remote()` called a plain, unbounded `TcpListener::accept()` on the main event-loop thread, so a slow WSL2/Xvfb/GTK boot blocked everything, not just that tab — fixed with a bounded 45s connect timeout that fails cleanly into the existing spawn-error UI path instead of hanging. (2) On tab close/crash-recovery, `Drop for EngineTab` force-killed the WebKit case's `wsl.exe` relay with zero grace period — that only kills the Windows-side process, not the actual Linux-side tree (Xvfb, GTK, the engine-host binary itself), leaving orphans running indefinitely; fixed by waiting up to 3s for a graceful WSL2-side exit first. The same unbounded-`accept()` pattern also existed in `accept_local_pair` (Servo/CEF's same-machine spawn) — lower risk since there's no cold-VM-boot equivalent, but hardened the same way regardless (a 10s bound, much shorter than WebKit's 45s since a same-machine child that hasn't connected within a few seconds has failed, not merely booted slowly). **Fixed (follow-up):** the `Drop for EngineTab` fix above only runs on browser-ui's own clean exit path — it never fires at all when browser-ui.exe itself is force-killed (`taskkill /F`, a crash) rather than exited normally, since no Rust destructor runs on that kind of process death. In that case, `engine-host-webkit`'s main loop kept polling GTK, capturing frames, and silently re-attempting now-dead sends forever — confirmed live, ~45% CPU indefinitely, wholly orphaned (no Windows-side process left to tear it down). Root cause: its reader thread already detected the dead control socket (Windows still closes the TCP connection on process death regardless of Drop, so `recv` reliably got an `UnexpectedEof`) but only broke its own loop silently instead of telling the main loop to exit. Fixed by having that `Err` path synthesize a `Shutdown` into the same channel the real message uses, reusing the existing clean-exit code path — see `engine-host-webkit/src/main.rs`'s reader thread. Only covers a parent that's actually gone (socket closed by the OS), not one merely hung-but-alive with the socket still open — no `Err` would fire in that case.
- **Fixed:** a headless `ENTER`/`ESCAPE`/`ARROWDOWN`/`ARROWUP` command immediately followed by `QUIT` with no delay between them (e.g. a fast test script) could exit the app before the earlier command was ever consumed, silently dropping it — `DebugCommand::Quit` used to call `event_loop.exit()` synchronously with no guarantee any frame ran first to process the pending flag. Fixed by deferring the exit one frame (`quit_after_next_redraw`) whenever a pending debug flag is still set when `QUIT` arrives, so the normal frame that would have consumed it gets to run first; a plain `QUIT` with nothing pending still exits immediately as before. Verified live via the exact back-to-back `ENTER`+`QUIT` sequence (temporary tracing confirmed the deferred path engages only when it should). **Same gap found and fixed for `SCREENSHOT`**: a `SCREENSHOT` immediately followed by `QUIT` had the identical problem (`pending_screenshot` is only consumed inside a `RedrawRequested`) — found live while testing a WebKit root-tab spawn, whose own cold-start delay made the race far more likely to actually trigger (a burst of queued stdin commands processed back-to-back the instant the blocking spawn call returns). `quit_after_next_redraw`'s trigger condition now also checks `pending_screenshot.is_some()`.
- **WebKit tab input (mouse, keyboard)** is wired up via synthetic GDK events, same as Servo/CEF. An earlier attempt at this caused a runaway-CPU event storm and was reverted (see project memory) — the fix was attaching a real `GdkDevice` to each synthetic event (`gdk_event_set_device`), which the first attempt never did. Verified via repeated live keystrokes/clicks with no CPU escalation, and (after the frame-freeze fix below) correct on-screen text — no dropped or doubled characters. Scroll is implemented the same way but not yet cleanly live-verified (test-harness input-injection reliability issues, not a known code problem).
- **Headless testing against WebKit specifically is measurably flakier than the other two engines.** The exact same test script, unmodified, has been observed to succeed and then completely fail (a command's handler never even firing) on back-to-back runs, whenever a concurrent WSL2/Xvfb/GTK process is involved — confirmed directly via temporary tracing, not assumed. Not a deterministic app bug (Servo/CEF headless tests don't show this); budget generous real wall-clock time (10s+ before the first command, several seconds between each subsequent one) for any WebKit headless test, and re-run once before treating a no-effect result as a real regression.
- **Fixed:** an engine-swapped-to-WebKit tab's rendered frame used to go permanently stale after respawn (title/URL kept updating, the visible content never did) — `GtkOffscreenWindow`'s backing surface never actually adopted a post-spawn `Resize` message's size, so the old size-matching gate on sending `FrameReady` never passed even once. Fixed by sending whatever size the captured pixbuf actually is, rather than requiring it to match what was requested. Verified live (a real page navigated to and rendered correctly after an engine swap).
- Page-triggered new tabs (ctrl+click, `target=_blank`, `window.open`) work for CEF, WebKit, and WebView2 tabs — verified live for WebKit and WebView2 (clicking a `target=_blank` link spawned a real child node in the graph at the right URL; for WebView2, confirmed via process count going from 1 to 2 with no second window ever becoming visible). Servo tabs don't send these — its popup-interception API doesn't fit this project's process-per-tab architecture (see `ipc_protocol::EngineToHost::OpenTabRequested`'s doc comment). **Confirmed safe, not just assumed:** clicking a `target="_blank"` link on a Servo tab is a clean no-op — `servo`'s `WebViewDelegate::request_create_new` has an empty default body when left unimplemented (as this project leaves it), so the click registers (visible focus outline) but nothing else happens — no crash, no hang, no phantom tab, no same-tab navigation, confirmed via a live headless-mode test with a `data:` URI test page.
- **WebView2 input is script-driven, not OS-level, and key events are unimplemented.** Three rounds of OS-level input injection (raw `WM_*` messages, Composition hosting's `SendMouseInput`/`SendPointerInput`, `MoveFocus` plus raw messages) all failed live — Chromium's real input pipeline silently ignored them. The working approach (round 4) dispatches small `ExecuteScript` snippets instead: `elementFromPoint().click()` for clicks, `scrollBy` for scroll, `execCommand('insertText', ...)` for text entry — all confirmed live. `KeyDown`/`KeyUp` remain no-ops: WebView2 has no CEF-style synthetic key-event injection API, so Enter-submits-a-form, Backspace-deletes-a-character, and arrow-key scrolling stay inert on WebView2 tabs specifically (deliberate round-4 scope, matching this project's actual use of links/buttons/forms rather than hover- or keyboard-driven UI) — see `engine-host-webview2/src/input.rs`.
- Favicons show for Servo, WebKit, and WebView2 (`ICoreWebView2_15::GetFavicon`, a real native API — verified live). **WebKit favicon: root cause found and fixed.** A `WebContext` favicon-database directory set at startup makes `WebView::connect_favicon_notify` fire at all (necessary), but that signal — and `WebView::favicon()` — are a *passive* property reflecting whatever the favicon database already has cached; nothing was ever actually asking the database to fetch a given page's icon. The real trigger is a separate async API, `FaviconDatabase::favicon(uri, cancellable, callback)`, called once a page finishes loading. Verified directly against the database file (not just a screenshot, given this project's WebKit-headless-test flakiness — see below): navigated to a real page, confirmed the domain now appears in the favicon database's own WAL file on the WSL2 side, where before the fix nothing was ever written for it. **CEF favicons: root cause found, not fixable from this project's side.** `on_favicon_urlchange` genuinely fires (confirmed with a fully-loaded, screenshotted real page, e.g. github.com) but its `icon_urls` list is always empty. Per CEF's own issue tracker (`chromiumembedded/cef` #3293/#3685), `windowless_rendering_enabled` forces CEF's legacy "Alloy" runtime (the modern "Chrome" runtime doesn't support off-screen rendering at all), and Alloy never fully wired up the chrome-layer favicon-candidate collection a normal windowed browser gets — the callback exists and is called, it just never carries real candidates in windowless mode. Not something a handler-side fix can work around; left as a graceful no-op (cosmetic, never load-bearing) with diagnostic logging kept in place in case CEF's behavior here ever changes.
- Graph-view thumbnails are downscaled (box-sampled to at most 256×192) before upload — Tab view's own live content stays full resolution.
- **Fixed:** two bugs found while building address-bar autocomplete. (1) The address bar's typed text used to snap back to the tab's real URL mid-keystroke — egui's own focus tracking transiently leaves the `TextEdit` for one frame the moment the suggestion dropdown's buttons first appear, so a naive `if !focused { resync }` fired on that blip; fixed by also treating non-empty suggestions as "still editing." (2) The exact same blip also hid the dropdown's own `Area` (buttons included) on the one frame a click landed on a row, silently swallowing the click — clicking a suggestion looked like it did nothing. Fixed the same way: gate the dropdown on the broader "still editing" check, not raw focus. (3) Separately, the very first HTTPS request `browser-ui`'s process ever makes (`ureq`/`rustls`'s one-time TLS setup plus a cold DNS+TLS handshake) was slow enough, the first time it happened to coincide with the user's first search query, to trip Servo's engine-host into a crash/respawn loop; fixed with a throwaway warm-up fetch at startup so that one-time cost is absorbed before the user can hit it.
- **Fixed:** a background Servo tab refocused from Graph view didn't repaint — content stayed black indefinitely even though chrome (title, spinner) kept updating and the engine-host process was alive. Root cause: `SetVisible(true)`'s capture-and-`FrameReady`-send block was gated on `notify_new_frame_ready` having fired again on its own, which never happens for a static page that received no input while hidden — the gate stayed shut forever. Fixed by forcing one repaint on the `false`→`true` transition instead of waiting for Servo to decide something changed. **Verification gap, now narrowed further (not fully closed):** added a `SETVISIBLE <bool>` headless debug command specifically to toggle a tab's visibility with zero `Resize` involved (the earlier suspicion — that `focus_tab`'s always-bundled `Resize` was masking the race — needed a way to rule it out). With `Resize` fully out of the picture, a negative-control test (temporarily reverting the fix, rebuilding, retesting) *still* didn't reproduce a black screen — meaning `Resize` wasn't the (or wasn't the only) masking factor. Something in Servo appears to keep re-arming `notify_new_frame_ready` periodically even for a page that looks static (a compositor heartbeat, caret blink, or similar), so `frame_ready` is essentially never caught sitting `false` at the exact instant a real toggle happens within a scripted multi-second window. The fix remains correct by inspection and provably safe either way (worst case: one harmless extra repaint) — the `SETVISIBLE` command is kept as a tool for whoever next has better luck (or a way to force Servo fully idle first) pinning down the precise repaint cadence needed for a deterministic repro.
