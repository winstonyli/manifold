# Manifold

A browser where each tab can run on a different rendering engine — Blink (via CEF), Servo, WebKit (via WebKitGTK), or Blink again (via Microsoft Edge WebView2) — and the engine backing a tab can be swapped live without closing it.

Status: [ROADMAP.md](ROADMAP.md) lists what is planned and [CHANGELOG.md](CHANGELOG.md) what each release shipped. Dated history (what was tried and measured, 2026-09 on) is in [docs/devlog.md](docs/devlog.md); open items from it are in `PARKED.md`.

## Architecture

```
manifold                  winit + wgpu compositor, process manager, swap logic
manifold-view-servo       Servo, same-machine child process (named pipe + shared memory)
manifold-view-cef         CEF (Blink), same-machine child process (named pipe + shared memory)
manifold-view-webkitgtk      WebKitGTK: native on Linux, hosted inside WSL2 on Windows (TCP transport either way: no shared memory across the VM boundary)
manifold-view-webview2    Microsoft Edge WebView2 (Blink), same-machine child process (named pipe + shared memory)
manifold-view-pdfium      one-shot PDF renderer: `<exe> <path>` writes one RGBA frame to stdout (`manifold_view_protocol::render`)
manifold-view-protocol    shared message types + both transports
manifold-pages            the `manifold://` pages (static HTML) and their router; every engine host serves them through its own scheme hook
manifold-hosts            the host table: one row per engine host (exe, build folders, delivery, runtime); std only, and only manifold and gate may depend on it
```

Only `manifold-view-webkitgtk` is Linux-only (no Windows WebKit embedding exists); everything else builds natively on Windows. `manifold` itself (and `manifold-view-protocol`) also compiles and passes its unit tests on Linux (checked under WSL Ubuntu, 2026-10-02: `cargo check -p manifold`, `cargo test -p manifold`), and runs there under WSLg in `--headless` mode, including CEF tabs (a visible window there can take down WSLg's own compositor, see the on-demand CEF entry); `manifold-view-cef` builds there too (see the on-demand CEF entry below for `CEF_PATH`). Windows-only crates are `[target.'cfg(windows)'.dependencies]`, Windows-only calls are `cfg`-gated, and what has no Linux counterpart yet says so instead of failing silently (WebView2 is Unavailable, "needs Windows"; a WebKit tab starts the host directly; Open Containing Folder toasts the same; engine hosts are not killed with a force-killed manifold, said once on stderr). `manifold` and `manifold-view-protocol` need no GTK on Linux: `rfd` 0.15 resolves to the XDG portal there, and only `manifold-view-webkitgtk` pulls `gtk-sys`. Building on Linux keeps `CARGO_TARGET_DIR` off `/mnt/c`, e.g. `CARGO_TARGET_DIR=$HOME/mf-target cargo check -p manifold`.

**Engines by OS** (2026-10-23; the app-side switch is `Host.os` in the host table (`crates/manifold-hosts`), the OS each host is built for, which `Host::built_for` resolves and `process_manager/runtime.rs` reads; the pick-up rules are in `process_manager/availability.rs`). The principle is each OS's own system webview plus CEF and Servo; only Windows is built, released and tested today.

| Engine | Windows | Linux | macOS |
|---|---|---|---|
| WebView2 (Blink) | native; frames by `Windows.Graphics.Capture`; released | n/a | n/a |
| CEF (Blink) | released; hash-pinned download | layout checked against the linux64 archive, install never run; no release job, no pin | no `CefPlatform` entry (needs an app-bundle layout), no pin |
| Servo | released; hash-pinned download | not restricted by the app; not built or run here | not restricted by the app; not built or run here |
| WebKit | WSL2 + Ubuntu + `xvfb-run`, TCP frames; the host is downloaded on demand (built in `release.yml` on `ubuntu-22.04`, pinned under `linux-x64`; built and pinned in a dry run, 2026-10-23, see Releases below) | the host builds (CI runs only the app's tests); the app starts it directly over loopback TCP (written 2026-10-23, run only as far as the pure launch tests) | none; the native engine there is WKWebView, a new host that needs off-screen frame capture (unspiked) |

Why WebKitGTK stays on Linux: the host crate is mostly portable GTK3 (a `GtkOffscreenWindow` rendered to a pixbuf, input as synthesized `gdk::Event`s, a plain TCP or pipe transport), but the WebKitGTK library has no maintained Windows or macOS build (WinCairo and the Cocoa port are different ports); its web process, sandbox and compositing lean on Unix sockets, bubblewrap, EGL and X11 or Wayland. That is upstream knowledge, not checked in this repo. The offscreen window is a GTK3 widget: see PARKED "WebKit host on GTK4".

**Which host runs, and whether it speaks this build's protocol** (2026-10-29, plan `docs/superpowers/plans/2026-10-29-host-protocol-stamp.md`). A built host runs in place: from its dev build folder first (`target-servo/debug/` for Servo, `target-linux/debug/` for WebKit, found by walking up from `manifold.exe`'s folder, only in a build that pins no hosts, so never in a release), then from beside `manifold.exe` (CEF only as its `cef-runtime/` copy, the one a tab runs); otherwise the host downloaded or extracted into `engine-hosts/` runs (`run_in_place` and `view_binary_path` in `crates/manifold/src/process_manager/availability.rs`). Every host exe carries the protocol number it speaks, in a `.mfproto` section (`crates/manifold-view-protocol/src/stamp.rs`). The app reads it from the host that would run in place, never from `engine-hosts/`, whose files are hash-pinned. A host speaking another protocol, or carrying none (built before 2026-10-29), reads Unavailable wherever engines are listed and is refused before spawning, with one reason that names which side to rebuild: "the engine host speaks protocol 7, manifold speaks 8; rebuild the engine host", or "rebuild manifold" for a newer host. Its failed card says "unavailable (click for why)", and the click explains instead of offering a download. The handshake check stays as the backstop for a host the app does not read first: its failed card gives the same reason, and the tab is not restarted. With a custom CEF folder set, the host a tab runs can differ from the one the app reads (PARKED "Host protocol stamp").

**CI** (`.github/workflows/ci.yml`) runs on every push and pull request: on Windows, `cargo fmt --all --check`, the pre-commit hook's clippy, and `cargo test` for the hook's crates; on Linux, `cargo test` for the crates that build there without GTK. The crate lists are in the workflow. CEF (a download, CMake, ninja), Servo (a 33-minute build), WebKit (WSL) and the probes (a desktop and a GPU) stay local.

**A graph level's own source, behind one seam (`level.rs`):** shared graph chrome (fit/Reset View, the minimap, the LOD card count, the settle key, right-click hit-testing, `EXPORTSTATE`'s `cards`, edges and layout) reads the current level through `App::level_items`/`level_edges`/`layout_current_level` instead of walking `self.nodes`/`current_group` directly. The stored-node graph is one source; a JSON level (`json/level.rs`) is a second, read-only one built from a Json node's parsed value instead of `self.nodes`. A third level kind needs its own `Origin` arm and painter, its own state on `App`, and a branch in each of `level_items`, `level_edges`, `layout_current_level` and `insertion_group` (those branches are `if let` chains, so the compiler won't list them for you); the chrome that reads those methods (fit, minimap, LOD count) needs no changes. Moving to an `enum LevelSource` would make the compiler enforce that (PARKED.md, LEVEL-SOURCE).

**A card is its type (since 2b-6):** a card's identity is `CardKind { ty, tags }` (`App::card_kind`, `card_kind.rs`), read from the document node's `Mirror::ty` plus a `Loaded` tag for a live tab; draw order, restorability and containment come from the `caps/` tables and edge table, not from an enum; click action, the Del verb, card style, the body painter, menus and parts of `drop_action` still `match` on the type constant (`TYPE_*`), and card size and filter text match on `Runtime`. Live per-card data (webview, edit buffer, decoded image) is `GraphNode.runtime`, an `enum Runtime` in `node.rs` (a group has `Runtime::None`). `NodePayload`, `ItemNodeKind`, `GroupPayload` and the caps bridge no longer exist, and a unit test (`deleted_names.rs`) fails if a source names them again. Plan and Outcome: `docs/superpowers/plans/2026-10-06-node-model-2b-6-enums-to-type.md`.

**Module layout of `crates/manifold/src` (since the 2026-10-09/10 main.rs split, `main.rs` 3,895 to 1,108 lines, 651 on 2026-11-04):** `main.rs` keeps `struct App` (61 fields on 2026-11-04), its `Default`, `ContentSource`/`WebBody`, the settings-save constants and `fn main`. `App`'s methods live in child modules as `impl App` blocks, which can read its private fields, so a moved method is `pub(crate)` only if another file calls it. By area: *views* `graph_ui` (Graph view, camera), `card` (card frame and painters), `tab_view`, `image_view`, `json/ui`, `popups`, `settings_page`, `node_menu`, `chrome_ui` (toasts, `build_ui`, toolbar buttons), `theme`; *behaviour* `tabs` (spawn, focus, split, destroy), `groups`, `node_store` (id allocation, store open, node removal), `node_ops` (close, mute, pin, bookmark, print), `graph_nav`, `view_modes`, `shortcuts`, `fetched`, `closed`, `viewport` (geometry, zoom, navigation), `session_files` (settings, named sessions, demo), `reveal`, `event_loop` (winit loop, engine messages), `omnibar`, `debug`; *model and data* `search/` (page text, BM25 index, topic clustering), `node`, `mirror`, `caps/`, `card_kind`, `level`, `links`, `jar` (with `jar/defs`), `names`, `store/`, `session_sync`, `local_state`; *plumbing* `gpu`, `net`, `process_manager`, `view_install`, and the fetchers. `App`'s state is being grouped into sub-structs with their own `reset()`/`forget(id)` (`link: LinkGesture`, `interaction: GraphInteraction`, `spawns: SpawnTracker`, `scoped: NodeScoped`, plus `camera`, `address_bar`, `find`); each `forget` destructures `Self` without `..`, so a new field fails to compile until handled. A test block of 250 lines or more moves to `<module>/tests.rs` (the parent ends with `#[cfg(test)] mod tests;`; `main.rs` uses `#[path = "main/tests.rs"]`); a smaller one stays inline. Source-scanning tests (`names`, `every_id_field_of_app_is_forgotten_or_excused`, which reads `main.rs` and `node_store.rs`) read specific files, so a method moved between files can fail one: fix the test's file list, not the move. Each move was proven by an identical sorted `cargo test -- --list` before and after, plus fmt, clippy, tests and the light gate. Grouping files into layer directories is parked: PARKED.md, "Layer directories for source files".

## Prerequisites

- **Rust**: the toolchain `rust-toolchain.toml` pins (rustup installs it on first use). Nothing needs nightly features; it is pinned so a clippy update can't fail the `-D warnings` hook with no code change.
- **Visual Studio 2022, 17.14 or newer.** Older toolsets are missing STL symbols that Servo's build needs — this is a hard requirement, not a suggestion.
- **A real `ninja.exe`** on PATH (`scoop install ninja`), for CEF's build script.
  - If a Chromium `depot_tools` checkout is also on your PATH, **exclude it** for this project's builds — its extensionless `ninja` shell script shadows the real `ninja.exe` and breaks the CEF build. See the "Building" commands below, which strip it automatically.
- **WebView2 Runtime** — preinstalled on Windows 10 1803+/Windows 11; if missing, `manifold-view-webview2` exits before connecting with one `manifold_view_protocol::HOST_FATAL` line, "WebView2 runtime not found (0x80070002): install the WebView2 runtime (Microsoft Edge WebView2, Evergreen) from ...", which the tab's failed card shows (before 0.2.0 it panicked creating its environment and respawned in a crash loop). Simulate it with `WEBVIEW2_BROWSER_EXECUTABLE_FOLDER` set to an empty folder. A runtime that is found but fails when the host, already connected, creates its environment or controller (damaged, or an unusable user-data folder) ends the same way: the host sends `Crashed` with the `HOST_FATAL` line and exits, and the tab is left as a failed card naming it with one toast, not restarted (`tabs::after_crash`; it used to panic and respawn three times, then say only "engine-host connection lost"). Simulate it with `WEBVIEW2_USER_DATA_FOLDER` set to a file: "WebView2 couldn't create its controller (0x80080005: Server execution failed); ..." (2026-10-04). Check via: `reg query "HKLM\SOFTWARE\WOW6432Node\Microsoft\EdgeUpdate\Clients\{F3017226-FE2A-4295-8BDF-00C3A9A7E4C5}" /v pv`.
- **WSL2, distro `Ubuntu`**, with:
  ```bash
  sudo apt-get install -y libwebkit2gtk-4.1-dev libgtk-3-dev xvfb build-essential
  ```
  (Rust/cargo must also be installed inside that WSL2 distro, separately from the Windows-side toolchain.)

## Building

**Windows-side crates** (`manifold`, `manifold-view-cef`, `manifold-view-webview2`, `manifold-view-pdfium`) — from a regular shell at the repo root:

```bash
PATH=$(echo "$PATH" | tr ':' '\n' | grep -v -F "depot_tools" | tr '\n' ':') cargo build -p manifold -p manifold-view-cef -p manifold-view-webview2 -p manifold-view-pdfium
```

The `PATH` filtering is only needed if `depot_tools` is on your PATH; harmless otherwise.

**Servo engine-host** — built into its own target directory, which keeps its dependency tree out of `target/` (see "Building Servo on its own"); manifold runs it from there, and the sync puts its DLLs beside it:

```bash
CARGO_TARGET_DIR=target-servo cargo build -p manifold-view-servo && target/debug/gate.exe sync-runtime-deps
```

**WebKit engine-host** — built *inside* WSL2, into its own target directory (it can't share `target/` with the Windows build — different OS, different toolchain):

```bash
wsl.exe -d Ubuntu -- bash -c 'cd "/mnt/c/Users/<you>/Documents/GitHub/manifold" && CARGO_TARGET_DIR=target-linux cargo build -p manifold-view-webkitgtk'
```

Adjust the path for wherever this repo actually lives on your machine (WSL2 sees your Windows drives under `/mnt/c/...`). `rust-toolchain.toml` applies there too: the first build makes WSL's rustup install the Linux build of the same nightly, and `target-linux` rebuilds once if WSL was on another toolchain.

### Runtime-file placement (required after every build)

Cargo doesn't do this itself — see the `TODO` on `view_binary_path` in `crates/manifold/src/process_manager/availability.rs`, which also says where each host runs from. Both CEF and Servo need extra files placed next to their binaries after each build, because they'd otherwise collide (both ship an ANGLE `libEGL.dll`/`libGLESv2.dll` under the same filenames, and Windows resolves an implicit DLL dependency from the loading EXE's own directory first — whichever copy landed there last silently wins for *both* engines).

`manifold-view-webview2` doesn't need this: WebView2Loader is a single small loader, statically linked by the `webview2-com` crate (or at worst one lone DLL) — none of the ANGLE-style same-filename collision the other two have.

Run this after every build that touches `manifold-view-servo` or `manifold-view-cef`:
```bash
target/debug/gate.exe sync-runtime-deps
```
It reads each host's layout from the host table (`manifold_hosts::ALL`, `crates/manifold-hosts/src/lib.rs`) and puts its runtime files beside the host manifold runs: Servo's ANGLE DLLs beside `target-servo/debug/manifold-view-servo.exe`, and CEF's runtime, with the CEF host itself, in `target/debug/cef-runtime/`. Each file comes from the build-script output in the host's own build folder first (`target-servo/debug/build/` for Servo) and from `target/debug/build/` only when that holds none, under `<crate>-<hash>/` or `<crate>/<hash>/` (where newer cargo nightlies put build-script output; `mozangle` for Servo's DLLs, `cef-dll-sys` for CEF's runtime); within one build folder it takes the newest match. A host whose build folder does not exist is skipped with one line (a tree with no `target-servo/` syncs CEF alone); the run fails only when no host with files to place has its build folder. A file found in no build output is kept, and said so, when it is already in place; otherwise it is an error when its host exe is built, and skipped when it is not. So a CEF build that left no runtime in `target/debug/build/` (a `CEF_PATH` build resolves it outside `OUT_DIR`) and has none in `target/debug/cef-runtime/` yet gets an error saying to copy the runtime there, and the CEF host is copied into that folder only once the runtime is in it. It `cmp`s each against the copy already in place and only recopies what's actually stale (safe to run any time — a no-op if nothing changed). Every step runs even when one fails; the failures are listed at the end, and a file a running host holds open is named with "close manifold and run again". Not a build.rs: a build script only sees its own crate's `OUT_DIR`, not a sibling crate's, and there's no reliable cross-crate coordination here without those upstream crates cooperating (they don't) — a plain script is simpler and more honest than fighting Cargo's model.

Why this needs a script at all rather than a one-time manual copy: Cargo has regenerated the `mozangle-<hash>`/`cef-dll-sys-<hash>` fingerprint directory these live under even on a rebuild that touched neither `Cargo.toml` nor `Cargo.lock`, leaving a stale copy in place that keeps working right up until it silently doesn't (Servo: panics with `egl function was not loaded`; CEF: silently runs stale code). The script picks the candidate whose own output *file* has the newest mtime, not the containing directory's — a build touches every candidate directory's own fingerprint bookkeeping on every invocation regardless of whether it actually recompiled that crate, which can leave several near-identical timestamps and make directory-mtime-based "newest" ambiguous.

A rebuild also tends to leave the *previous* hash's directory behind alongside the new one (Cargo doesn't clean up an old fingerprint just because it's no longer used) — these accumulate across sessions and are a repeat cause of this project filling the disk. Safe to prune anything under `target/debug/build/{mozangle,cef-dll-sys}-*` except whichever one `gate sync-runtime-deps` just used — re-run it afterward to confirm nothing needed recopying. Getting this wrong (deleting the wrong one) just means the next build regenerates whatever's missing, not silent breakage — but it's wasted rebuild time.

## Branches

Since 2026-10-06, `main` is the only long-lived branch and releases are tags. (From 2026-09-25 to then, work went on `dev` and `main` moved only at releases through `git merge --no-ff dev`; `dev` was merged into `main` and retired. The release merges `v0.1.0`, `v0.2.0` and `v0.3.0` remain in `main`'s history.)

- Commit and push to `main`. Feature branches and worktrees branch from `main` and merge back into it.
- A hotfix for an old release branches from its tag as `release/x.y`, is tagged like a release, and the branch is deleted after. The fix is also applied to `main` (cherry-pick or merge).
- Everything on `main` up to `2a88b50` predates the branch convention and is the pre-release baseline.

## Releases

- A release is a version bump commit on `main` (workspace `version`, plus `Cargo.lock`, plus a new top entry in `CHANGELOG.md`), then an annotated tag `vX.Y.Z` on it whose message is that entry, made by `target/debug/gate.exe release-tag vX.Y.Z` (it refuses unless the tree is clean, the workspace version is X.Y.Z and the changelog has the entry, builds `manifold vX.Y.Z`, a blank line and the entry body with the same code `release-check` reads it back with, and tags with `--cleanup=verbatim`, which the default cleanup would not do to the `###` headings; a hand-built message once failed `release-check` on the pushed tag, 2026-10-25), then pushing the tag runs `release.yml` (see Releases), which leaves a draft release for you to read and publish. `git tag -l` and `git log --first-parent --decorate` list the releases.
- Releases run on GitHub Actions (decision `docs/decisions/2026-10-18-hosts-in-the-release.md`, which replaced the `hosts-KIND-FP` design of `docs/superpowers/specs/2026-10-16-ci-release-design.md`). Pushing an annotated tag `vX.Y.Z` runs `release.yml`: `gate release-check` (tag message is `manifold vX.Y.Z`, a blank line and the `CHANGELOG.md` entry's body; workspace version), the downloadable hosts (CEF: `manifold-view-cef.exe`, static CRT; Servo: `manifold-view-servo.exe` at 129 MB plus its ANGLE `libEGL.dll` and `libGLESv2.dll`, dynamic CRT; the Servo build adds about 40 minutes) with a manifest of their sizes and SHA-256 hashes (`dist/manifold-vX.Y.Z-windows-x64.host-pins.json`, written by `gate release-pins`, which copies into `dist/` each host the host table in `crates/manifold-hosts` marks as downloaded, a host built for another OS from the `webkit-host` job's artifact), the embedded WebView2 host and PDF view (`gate release-embedded` copies them into `dist/embedded/` and writes their hash records; both subcommands print the build variables as `NAME=path` lines, which `release.yml` appends to `$GITHUB_ENV` for the step that builds `manifold.exe`), `manifold.exe` built with `MANIFOLD_HOST_PINS=<that manifest>` (`build.rs` embeds it and `crates/manifold/src/view_install/host_pin.rs` parses it: the hash compiled into the exe is the trust anchor, the URL is not trusted, and a host's URL is `releases/download/v<exe version>/<file>-<platform>`), `gate package`, `gate release-verify` (the manifest pins exactly the host table's files for the release's platform, the host files in `dist/` match it, and each embedded host's copy matches its hash record), then a draft release (the draft is the publish gate; run by hand on a branch, `release.yml` does the same build without a release or tag and uploads `dist/` as an artifact, so a workflow change needs no throwaway version) holding the exe, its `.sha256`, the embedded hosts' hash records, the manifest and each host as `FILE-PLATFORM`. A build with no manifest (dev, the gate) pins nothing; a debug build also reads `MANIFOLD_HOST_PINS_FILE` (the gate's engine-states shots use it). WebKit's host is built by the `webkit-host` job (`ubuntu-22.04`, the oldest Ubuntu with `libwebkit2gtk-4.1`, so its glibc starts on older distros) and pinned under `linux-x64` (dry run 40006630810, 2026-10-23: the ELF is in the manifest and `dist/`, all libraries resolve in WSL Ubuntu, glibc floor 2.34; not yet started under a real tab). The release is that one exe: CEF's, Servo's and WebKit's hosts are downloaded on demand into `engine-hosts/` (WebKit's is a Linux ELF pinned under `linux-x64`; WSL runs it straight from that Windows folder, and a built host beside the exe or in the dev tree's `target-linux/debug/` wins over the download; WSL itself, a distro named Ubuntu, `xvfb-run` and the WebKitGTK libraries are not part of the download), each checked against its pinned hash, with a per-engine `<engine>.host` marker listing the installed files' hashes (written last; the 5 s disk poll reads only the marker) and a re-hash when a tab spawns. A host is pinned by hash, so **after an update the downloaded host reads Update needed and must be reinstalled** (Settings, Engines; every release rebuilds its hosts and the output is not bit-reproducible). An engine whose host this build pins no download for, and that has no built host, reads Unavailable ("this build has no Servo download"); dev builds and Linux CI pin nothing and keep the in-place lookup ("Which host runs, and whether it speaks this build's protocol"). `gate package [exe]` runs the finished exe alone in a temp folder (see Packaging); `gate install-check cef|servo EXE` (a published release only) has that exe install the engine from the network, as a Download click does (v0.7.1: installed in 28 s, run `install-check-v071b`; v0.8.0: CEF 28 s, Servo 25 s, run `install-check-v080`).
- Packaging: the release is `dist/manifold-v<version>-windows-x64.exe` from `release.yml` (about 27 MB with the 0.9 MB WebView2 host embedded; embedding the 4.6 MB PDF view as well measured 23.5 MB -> 28.8 MB on a non-static-CRT release build, 2026-10-12; no zip, no README or PACKAGING.md beside it). `gate package [exe]` (default: the newest `dist/manifold-v*-windows-x64.exe`; a draft release's exe works too) copies that exe ALONE into a temp folder and checks it: it imports no `vcruntime140`/`msvcp140` (`llvm-objdump`; the release links the C runtime statically via `RUSTFLAGS="-C target-feature=+crt-static"`, set by `release.yml` only, and CEF's wrapper is built `/MT` by `cef-dll-sys` already), it runs headless with `APPDATA` redirected, `VIEWSTATE cef` and `servo` read Not installed (with the download size when the release's pin manifest pins them), a WebView2 tab loads a local page with the host extracted from the embed, and a PDF node renders its fixture through the extracted PDF view (the one download: PDFium, once).  A local CEF build needs `depot_tools` off `PATH` (the CI runner has none); a CMake cache from an earlier failed CEF build (`target/release/build/cef-dll-sys/<hash>/out/build`) must be deleted by hand. The downloaded Servo host and its `libEGL.dll` are the exception to the static CRT (mozjs and mozangle are `/MD`): they import `vcruntime140`/`msvcp140`, so Servo needs the Visual C++ Redistributable even though `manifold.exe` does not (the Servo download dialog warns when `vcruntime140.dll`, `vcruntime140_1.dll` or `msvcp140.dll` is missing from System32). Unsigned.
- Embedded PDF view: the same mechanism for `MANIFOLD_PDFIUM_HOST` (`manifold-view-pdfium.exe`, extracted to `engine-hosts/pdfium/` at the first PDF render; `gate release-embedded` records its hash in `dist/manifold-<tag>-windows-x64.embedded-pdfium.sha256`, next to the WebView2 host's `.embedded-webview2.sha256`; `gate release-verify` checks both). The PDF view exe is `manifold-view-pdfium` in the dev tree too, found beside `manifold.exe` before the embedded copy; `manifold.exe` itself no longer links PDFium's bindings. The crates are `manifold-view-*`; the four web view exes are `manifold-view-*` too (before the next release they were `manifold-engine-*`).
- Embedded WebView2 host: a build with `MANIFOLD_WEBVIEW2_HOST=<path to the host exe>` (set by `release.yml` from `gate release-embedded`'s output) carries that host inside `manifold.exe` and extracts it to `engine-hosts/webview2/` at the first WebView2 spawn (`crates/manifold/src/view_install/embedded_host.rs`). Dev builds and the gate leave the variable unset, embed nothing and use the sibling host, so neither exercises the embed; only `MANIFOLD_WEBVIEW2_HOST=<abs path> cargo test -p manifold embedded_host` (use a separate `CARGO_TARGET_DIR`, as the variable changes the build) and a release build do.
- Packaging policy: packaged builds offer CEF on demand, opt-in, never as the default engine, and never bundled (spec `2026-10-02-engine-install-design.md`).
- Release checklist: if the `cef` crate moved, re-pin CEF for every pinned platform (`target/debug/gate.exe cef-pin [--platform <id>] <prefix>`, a download per platform; spec `2026-10-02-engine-install-design.md`, "Platforms") before tagging.

## Search

The omnibar finds a card by what its page says, not only by its title and url. Each tab's visible text is asked of its engine a moment after a load ends and before the tab sleeps (`QueryPageText`, protocol 6) and appended to `text.log` in `search/` under the profile folder (`profile::search_dir`). Nothing leaves the device: the index is a hand-rolled BM25 in memory (`search/index.rs`), rebuilt from `text.log` on a worker thread at every start and never saved. A tab in an ephemeral jar is never read, and turning a jar ephemeral deletes its tabs' text at the next pass. `search/sync.rs` keeps the index equal to the document once a second: it fingerprints every card's text (title and url, a note's text, a name, a file name, the stored page text) and queues what changed, so a rename, a note edit (a second after the edit, not per keystroke), a close and a permanent delete need no hook each. Settings, "Clear search index" deletes `text.log` and empties the index; it says the same in a line above the button.

A query is the AND of its words, the last one a prefix, ranked by BM25 (K1 1.2, B 0.75). The Graph dims cards the omnibar text misses, by title, url or page text (`App::node_matches`); the dropdown lists up to five tabs and up to five other cards, each with a snippet of the page text when that is what matched.

Startup build, measured 2026-10-23 on a 71 MB `text.log` (5 000 pages of 1 500 words, release): loading the log takes about 0.1 s, building the index from it about 19 s on the worker thread (see PARKED.md, "Saved search index"). Search works on what is built so far; the dimming and rows fill in as it finishes.

**Suggest groups** (spec `docs/superpowers/specs/2026-10-23-search-and-categorization-design.md`). Each card's text becomes a vector (`search/lsa.rs`: tf-idf rows, a seeded randomized SVD to 64 dimensions, so the same texts give the same bits in any order); a cosine says how much two cards talk about the same things. *Suggest groups* (toolbar sparkle, omnibar command, `SUGGEST`) clusters the level by average linkage (`search/cluster.rs`: cosine 0.2, at least 3 cards, at most 8 groups, at most 400 cards; 400 cards take about 100 ms in a release build) and offers each cluster as a ring round its cards and a chip with Accept and Dismiss. Nothing is grouped until accepted, an accept is one undo step, and an offer stands only while the level's cards are the ones it was made for. The ordinary settle knows nothing of topics: topic structure comes only from accepting a suggestion, which moves the cluster into its own level. An explicit "Arrange by topic" action (LSA-seeded positions with similarity springs) existed until 2026-11-01 and was removed: no topic force in the settle kept overlaps near the no-force baseline (PARKED "Shared topic input for similarity edges"; `git show cabfa377:crates/manifold/src/search/arrange.rs`).

**Drop and pin anchors (2026-11-01, spec docs/superpowers/specs/2026-11-01-scopes-nested-layout-anchor-design.md, Slice 1).** One stored register, `ANCHOR` (field 27: point, group, explicit bit), replaces the `pinned` bool (field 7, now reserved; an older session's pins are ignored). Pin writes an explicit anchor where the card is drawn; a drag release writes an implicit one where it lands. A card is held when its anchor is explicit, or implicit and written in the group it is in now (`Mirror::held`); the settle seeds a held card from its anchor point and keeps it there, and the settle key includes the held set, so a drop re-settles the neighbours around it. Unpin releases a pin only; Tidy (toolbar broom while a drop is held, omnibar "Tidy", `TIDY`) releases every drop at the level, and a local move the card's drop; Tidy, moves and folds are undoable with their anchors. Only the explicit bit counts as "pinned" (pin mark, menus, Pin All, idle-sleep exemption). JSON export drops anchors, so a copied or duplicated pinned card arrives unpinned.

## Headless mode (automated testing)

```bash
target/debug/manifold.exe --headless
```

`--script <file>` reads the commands from a file instead of stdin (EOF quits, as for stdin), and `--profile-dir <dir>` (or `--profile-dir=<dir>`) uses `<dir>` as the profile folder instead of `%APPDATA%manifold`. Together they let a run with no stdin and no way to set `APPDATA` stay isolated, such as one started by the elevated `Samply` task (`~/.claude/SAMPLY.md`), which otherwise would use the real profile. Any other argument, or a flag missing its value (a bare `--profile-dir`, an empty one, or one followed by another flag), is refused: manifold prints `manifold: <why>` and exits 2, rather than running on the real profile.

Runs the same app, but the window is positioned far off-screen (not `--visible(false)` — a genuinely invisible window's swapchain never successfully acquires a frame on Windows, DWM permanently reports it occluded; an off-screen-but-visible window keeps rendering normally while never overlapping the user's actual screen) and driven entirely by a text-command protocol read from stdin, one command per line, instead of real OS input. This exists so live GUI testing of this app doesn't have to fight Windows' foreground-lock (`SetForegroundWindow` can be silently refused while the user is active on their own machine — see project memory) or contend visually with whatever the user is doing. `EXPORTSTATE`, `EXPORTSESSION` and `EXPORTGROUP` replace their file atomically (written beside it, then renamed over it), so a script may read one as soon as it exists; `SCREENSHOT` writes in place, so wait for its size to settle.

Debug commands read and write any path the user can (the `EXPORT*` and `IMPORT*` commands, `SCREENSHOT`); they are for driving manifold from scripts and are not a security boundary.

Commands:
- `MOUSEMOVE <x> <y>`, `MOUSEDOWN <x> <y> [left|right|middle]`, `MOUSEUP <x> <y> [left|right|middle]`, `CLICK <x> <y> [left|right|middle]`, `DOUBLECLICK <x> <y>` — dispatched as genuine synthetic `winit::event::WindowEvent`s, not a logic bypass, so they exercise real egui hit-testing exactly like real input would.
- `SCROLL <x> <y> <delta_x> <delta_y>`
- `ADDRESSBAR <text>` — in Tab view, focuses the address bar, then types the text over its contents as egui key/text events, so suggestions update through the real `TextEdit` path.
- `ENTER`, `ESCAPE`, `ARROWDOWN`, `ARROWUP` are real `egui::Event::Key` presses injected into the next frame's input, not calls into the handlers. `winit::event::KeyEvent` has no public constructor, so they enter at the egui level; see `debug`'s doc comment. Headless mode marks the window focused for egui, which otherwise reports no widget focus in an unfocused window.
- `ENTER` — in the focused address bar, navigates using its text or the highlighted suggestion.
- `ESCAPE` — dismisses the suggestion dropdown, or leaves Item view (a maximized tab or image) for Graph view if none is showing.
- `ARROWDOWN` / `ARROWUP` — moves the address-bar dropdown's highlighted row (wrapping at both ends); a following `ENTER` accepts it.
- `EGUITEXT <text>` — types into whichever egui text field has focus ("New Jar..."'s field, a group rename), as an `egui::Event::Text` in the next frame's input; `BACKSPACE` is a real Backspace press there. With `ENTER`/`ESCAPE` they drive those fields end to end. Leading and trailing spaces are trimmed off the text.
- `TYPE <text>` — sends each character to the focused tab's page (not the address bar).
- `KEYPAGE <name>` — sends a KeyDown+KeyUp of the named key (`Enter`, `Backspace`, `ArrowLeft`, a single letter/digit, etc.) to the focused tab's page.
- `NEWTAB` / `CLOSETAB` / `FOCUSADDRESS` / `NEXTTAB` / `PREVTAB` — the `Ctrl+T`/`Ctrl+W`/`Ctrl+L`/`Ctrl+Tab`/`Ctrl+Shift+Tab` shortcuts' exact same effect, called directly (same rationale as `TYPE`/`KEYPAGE`: no public way to synthesize a real `Ctrl`-chorded `KeyboardInput`). `FOCUSADDRESS` is the one command among these that isn't instant — it drives a real `egui::Response::request_focus()`, which (immediate-mode) only takes visible effect starting the *next* frame, so it also forces a redraw itself rather than relying on some later, unrelated command to eventually trigger one.
- `SCREENSHOT <path>` — saves the next composited frame (chrome, any open dropdown, and content) as a PNG, read back directly from the GPU rather than `PrintWindow`/`CopyFromScreen` (see project memory's gotchas on GDI-handle exhaustion and foreground-lock unreliability with that approach). Unlike the toolbar's Screenshot button it shows no "Saved <path>" toast, which would cover the bottom-left of the window for 4 s, in later screenshots and under a script's next clicks.
- `EXPORTSTATE <path>` also lists what the last finished frame drew, so a probe asserts on state instead of pixels: `identities` (every `Identity::paint` icon: `kind` spinner|image|glyph|tile, `text`, screen `rect`; the JSON preview header's glyph is not logged, since it paints through `Identity::text`), `controls` (every widget with a name, as a screen reader hears it: its own label, or the text of what it is `labelled_by`, from egui's accesskit tree, which `--headless` and `--debug-commands` always turn on; `name`, screen `rect`, `selected` = toggled (the omnibar's highlighted row) or keyboard-focused (a history or bookmark row), `focusable` = a Tab stop (enabled and sensing focus, egui's own rule: a disabled button is named but not one); frontmost layer first; `identity::controls_in`. List rows are controls: `popups::list_row` and the omnibar's rows say they are buttons. `gate`'s `click_control` and `hover_control` find a control by name, and `State::popup_controls` gives the ones inside a popup, a dropdown's rows) and `open_popup` (the `AnchoredPopup` open, by name) and `group_suggestions` (the groups "Suggest groups" offers that still stand: `label` and `cards`). Recording is in `identity.rs` (`begin_icon_frame`, `drawn_icons`). `gate trail` asserts the strip's and address bar's tiles and the dropdown's rows through them. `TOGGLEPOPUP recentlyclosed` opens the graph toolbar's Recently Closed list.
- `ADDFILE <path> [x y]` — adds a file as the node its content makes (image, PDF, JSON, note, tab, or a download card); `x y` is a window point, like a drop there.
- `NEWJSON [x y]` — a new inline JSON card (empty object) at a window point; `DETACHJSON <id>` — move a file JSON card's value into the synced document and drop its path (toasts and changes nothing past the 10,000-leaf cap).
- `JSONEDIT <op> <pointer> [args]` — edit the open inline JSON level: `set <ptr> <json>`, `add <ptr> <key> <json>`, `insert <ptr> <index> <json>`, `remove <ptr>`, `rename <ptr> <to>`, `move <ptr> <to>` (`root` is the root pointer; `<json>` is the rest of the line). One undo step each; `json_level` reports `"editable"`.
- `JSONSELECT [pointer]`, `JSONTOGGLE [pointer]`, `JSONMORE [pointer]`, `JSONRELAYOUT`, `JSONSEARCH <text>` — drive the current JSON level (double-click a Json card to enter one): select an entry (empty pointer: the root) and pan to it if it's off-screen, collapse/expand a card, page a card's rows, clear saved card positions and relayout, and search keys and scalar values. `EXPORTSTATE`'s `json_level` (below) is `null` off a JSON level.
- `MOVETOGROUP <id> <group>` — the node menu's "Move into <group>" with explicit ids (a Join drop, which saves); ignored, with a note on stderr, unless the menu would offer that group (a sibling group). `EXPORTSTATE`'s `mirror_groups` maps every node id to its group as the instance shows it.
- `CLOSENODE <id>` — closes node `id` (any kind) as its card's Close or Delete does, setting `closed` on it so it lists in Recently Closed, and saves; an unknown id is ignored with a note on stderr. (It replaced `CLOSEGROUP`.) `EXPORTSTATE`'s card key `stored_type` is the type string as stored. It equals `type` except for an `image/*` other than `image/png`, a different case, or a type this build doesn't know, whose `type` is `application/vnd.manifold.unknown`.
- `REOPENNODE <id>` — reopens closed node `id` as the Recently Closed popup does (`reopen_node`), whichever replica closed it; `REOPENTAB` reopens the newest one this replica closed. `EXPORTSTATE`'s `closed` lists the Recently Closed ids newest first (`Doc::closed_roots`), and each entry of `links` has `shown`, true when both ends are cards on this replica (a link to a closed node stays stored and reads false).
- `GOBACK` / `GOFORWARD` — the focused tab's Back and Forward chips: a move in the tab's trail (the engine's own Back/Forward when its list agrees, else a load of the entry's URL), and at the trail's first page Back goes to the card the tab was opened from, Forward there back to the tab (`trail/nav.rs`; spec docs/superpowers/specs/2026-10-14-trail-design.md). `EXPORTSTATE`'s `trail` maps each tab with a trail to `{entries, depth, url, back_fork, forward_fork, lin_at, lin_len, left_to, back, forward}`: `depth` is 0 at the first page, `back`/`forward` are the chips' enablement, `back_fork`/`forward_fork` whether the chips show a branch marker.
- `LINK <a> <b>` — links card `a` to card `b`, as `a`'s "Link to..." row and a click on `b` do, and saves; a refusal (`NotLive`, `DifferentLevel`, `Exists`, ...) goes to stderr. `UNLINK <a> <b>` removes the link between them in either order (silent when there is none) and saves. `OPENEDFROM <child> <parent>` sets `child`'s opener, as its "Opened from..." row does. `EXPORTSTATE`'s `links` lists every stored link as `{id, from, to}` (hidden or dangling ones included), and `connecting` is pick-target mode's `{from, edge, targets}` or null. `EXPORTSTATE`'s `edges` lists the lines drawn at this level as `{kind, link, from, to, screen}` (`screen`: the curve's middle, t = 0.5, where a probe clicks a link line). `link_handles` maps each card that would show connect handles to its `{top, right, bottom, left}` screen rects. `connect_drag` is a running connect-drag's source or null, `dragging` the card being dragged or null.
- `RENAMEGROUP <id> <name>` — commits `name` as node `id`'s new name, as its rename field's Enter does (any node; a group takes the clean name, another node stores `name` as an override of its label, and an empty name clears it; an unknown id is ignored with a note on stderr), and saves.
- `DUPLICATENODE <id>` — duplicates node `id` (the whole selection when `id` is in it) beside the original, as the context menu's Duplicate does: a tab through `duplicate_tab`, anything else, a group's subtree included, through a pure snapshot (`duplicate.rs`), offset by 40 px; saves. `RENAMEGROUP` with no arguments is still `F2`.
- `NEWJAR <name>` — a new jar card at the current level, as the Jar page's "New Jar..." makes, with no edge; prints its id. `USEJAR <id> <jar-id|none>` — tab or group `id` draws its `jar` edge to that jar card, or clears it with `none`, as a Jar page row does. `JAREPHEMERAL <id> on|off` — jar card `id`'s Make or Stop Ephemeral, confirmed. `EXPORTSTATE` cards carry `jar`, `effective_jar` and `is_default`.
- `SETNOTETEXT <id> <text>` — note `id`'s box typed to hold `text` (the rest of the line, possibly empty) and blurred, which commits it (resolving any remote text held meanwhile) and saves.
- `MOVENODE <id> <x> <y>` — card `id` dragged to world point (x, y) and released: its document pos and drop anchor are written as a drag release writes them, and saved. `EXPORTSTATE`'s `mirror_names` (groups), `mirror_texts` (notes) and `mirror_pos` (every node) map ids to the name, text and document pos the instance shows, null where `EXPORTSESSION` leaves the field out. `mirror_anchor` maps every node to its anchor (`{pos, group, explicit}`) or null; the document JSON never carries it.
- `RESIZE <width> <height>`
- `LABEL <name>` makes a label (or finds the one with that name) and puts it on the selected cards; `LABELSELECTED <name> on|off` toggles it on the selection; `LABELRENAME <old> <new>`, `LABELDELETE <name>` and `SELECTCARDS [id...]` (sets the selection). `EXPORTSTATE`'s `right_panel` says what the right panel shows (`outline`, or `cards` with the selected ids and the one card described). `EXPORTSTATE` lists `labels` and each card's `labels`.
- `SUGGEST` — the toolbar's Suggest groups: clusters this level's cards by page text and keeps the clusters as offers (`EXPORTSTATE` `group_suggestions`). `ACCEPTSUGGESTION <n>` groups the n-th offer's cards (from 0) in one new group, one undo step. `ACCEPTSUGGESTIONLABEL <n>` labels the n-th offer's cards instead (one undo step). `TIDY` — the toolbar's Tidy: releases this level's drop anchors, pins stay (one undo step).
- `WAITTABS [secs]`, `WAITIDLE [secs]`, `WAITINDEX [secs]`, `SLEEP <secs>` (seconds, fractions allowed: `SLEEP 0.2`) — hold the commands after them, in order (default 60 s at most for the first three). `WAITINDEX` waits until every live http(s) tab outside an ephemeral jar has the text of the page it shows, and the search index has taken it in (an engine that never answers `QueryPageText` holds it to the timeout); `WAITTABS` waits until no tab spawn is in flight; `WAITIDLE` until typed input (`ADDRESSBAR` text, queued keys) has landed, no view transition runs, the Graph camera isn't easing or gliding (while the Graph shows), egui didn't ask for the next frame at once (a popup fade, hover easing, smooth scroll or a popup still sizing itself), no address-bar suggestion is on its way and the focused tab isn't loading, all for 3 frame ends in a row (it draws frames itself until then), so use it between `ADDRESSBAR` and `ENTER` and after a new tab's spawn, instead of a guessed `SLEEP`. A tab that hasn't reported its first load yet counts as not loading, so after an `ENTER` wait for something the page does (a request at its server) before `WAITIDLE`.
- `QUIT` — exits cleanly. Also sent automatically on stdin EOF, so a driving script that closes its write end doesn't leave the process hanging.

`gate smoke` (`crates/gate/src/smoke.rs`, the Rust port of the former `headless-smoke-test.sh`) is a runnable example (and a real regression smoke test): drives the address-bar autocomplete flow end to end through one headless instance on stdin and asserts each screenshot was actually produced and isn't suspiciously small, plus app state read back through the debug-only `EXPORTSTATE` command (whether it's in Tab view, the focused tab's URL, the dropdown's rows and which one is highlighted). It also covers Graph-view groups: entering and leaving one, tab drops inside one (reparent, the cycle refusal), ejecting a selected tab, and the overloaded and empty groups' border colors, read off a screenshot (read with the `image` crate). It also closes a group holding an image and a nested group and checks that `REOPENTAB` brings back the whole subtree, still nested. Those click cards where `EXPORTSTATE`'s `cards` puts them, polling until two exports agree, because the camera eases after entering a group. That's not visual-regression testing, but it catches wrong behavior as well as crashes. It polls that state instead of sleeping for DuckDuckGo's suggestions (a fixed 3 s wait was once too short, and an Escape with no dropdown up correctly left Tab view), and compares the searched query against the exact row it clicked or highlighted, so DuckDuckGo's changing order doesn't matter. `EXPORTSTATE` is separate from `EXPORTSESSION` because `EXPORTSESSION`'s JSON is the persisted import/export format, not a place for transient UI state. A card whose window has moved (`skip` > 0) also gives `earlier`, the screen point of its `+ N earlier` row (null otherwise); the smoke test's last JSON block drops a 1000-entry array, `JSONSELECT`s `/items/900` (the window moves, skip 900), `CLICK`s that point and checks the window grew up a page (skip 880). It runs in its own throwaway `APPDATA` profile (starting from just the root tab) and leaves other running manifold windows alone. Run it after `cargo build -p manifold`. Its suggestions come from a local server (`suggest.rs`'s `/ac/`, via the `MANIFOLD_SUGGESTIONS_URL` override of the autocomplete endpoint), so the address-bar checks no longer need the network (2026-10-02); the group-card checks stay timing-flaky (see Open below).

To run one session from a file of commands by hand: `target/debug/manifold.exe --headless --profile-dir DIR --script commands.txt` (`DIR` names the manifold folder itself, so the real `%APPDATA%\manifold` is never touched; the file's last line should be `QUIT`). A session to start from: `manifold.exe --import-json session.json --out DIR\session.mnf` builds the profile's session file from a JSON snapshot first. `gate profile` (crates/gate/src/profile.rs) is a worked example that writes its own command file and prints a per-phase table of redraws a second, frame time, input latency and CPU from the app's timing trace (`MANIFOLD_TRACE=<path>` writes Chrome trace events of the `frame`, `egui` and `render` spans, input arrivals and egui's repaint requests, `telemetry.rs`; Perfetto opens it; a script's `MARK label` cuts it into phases; `gate profile graph-idle --visible` measures a window with nothing to do); it needs a release exe at least as new as every source file under `crates/`, and says to rebuild otherwise. When `RUN_DIR` is set (`~/.claude/runs/run.ps1`), `gate profile` also writes the table's one-line summary as that run's `headline.txt`. `gate ab NAME SCENARIO [SECONDS] [--repeats N] [--quiet PCT] LABEL:VAR=value,...` (crates/gate/src/ab.rs) runs `gate profile --visible` once per arm per repeat, interleaved and each through `run.ps1` as `ab-NAME-LABEL-rN`, waits for total CPU under PCT (default 15) before each run, and prints the median frame time (with its range) and CPU per phase and arm; an arm is an environment switch such as `WGPU_BACKEND=vulkan`. `--debug-commands` runs the same file in a real window (`gate profile graph-frames 10 --samply --visible`), which tells egui it has focus, so scripted keys and clicks need no OS foreground (the elevated samply task cannot take it, and Windows blocks input injected from a non-elevated process into an elevated window). Piping commands on stdin to `--headless` also works (`gate launch-forms` launches that form).

`gate two` (`crates/gate/src/two/`, the Rust port of the former `two-instance-test.sh`) runs two (later a third, then a fourth, one at a time) headless instances on one shared, isolated `session.mnf` profile, exercising the store's multi-writer merge end to end. The scenarios keep the script's numbers 1 to 12 and run in the order 1, 2, 8 to 12, 3 to 7: (1) instance A imports a two-tab group and instance B adds a note, then both instances' `EXPORTSESSION` node sets agree; (2) A imports 200 notes -- enough ops to cross `COMPACT_MIN` and trigger a compaction on save -- while B stays open, B adds another note afterward, and both still agree with nothing lost (`session.mnf.prev` confirms A actually compacted); (8) A moves a new note into a new group (`MOVETOGROUP`) and B follows; (9) A and B move one note into two different groups back to back and end on one of them, nothing lost, no cycle; (10) A moves group G into H while B moves H into G, and both end on the same acyclic nesting without hanging; (11) A renames a group (`RENAMEGROUP`) and B follows, then both rename it back to back and end on one name; (12) A sets a note's text (`SETNOTETEXT`) and B follows, then both set it back to back and end on one text that a further save doesn't undo, then A moves the note (`MOVENODE`) and B's mirror and document follow. Scenarios 8 to 12 compare each node's group, name, text and pos in what A shows, what B shows (`EXPORTSTATE`'s `mirror_groups`, `mirror_names`, `mirror_texts`, `mirror_pos`) and the document. (3) A navigates a new tab to the nonce site, a local site that redirects to a fresh url on every load, and B's copy follows once without the two navigating each other (the site's request count must stop climbing); (4) A clicks a link on that site and B follows, then A's page navigates by script and B doesn't; likewise a single-page app's url change is followed from a click, not from a timer (the engine reports how each navigation started; the server counts urls asked for twice); (5) A navigates the shared tab to a local JSON file and B follows, and the document ends with exactly one more Json node, not one per instance; (6) A adds a note and is killed (`TerminateProcess`, not power loss -- the kill always comes right after an `EXPORTSESSION`, which saves first, so this exercises a replica vanishing, not recovery from a torn write), B exits cleanly, and a fresh third instance opened on the same profile still has A's note; (7) that third instance, now alone, types a url whose page navigates by script and quits, and a fourth reopens the tab at the script's url (the personal-state `live_url`), not the typed one. The nonce site is `crates/gate/src/nonce.rs`, served in process by a thread of `gate`, so the test reads its request counters directly; the JSON asserts (shared-node multiset, group, field agreement, no cycle) are `crates/gate/src/session.rs`. Every assertion prints a `PASS:` or `FAIL:` line (66 labels), polled until agreement instead of a fixed sleep. The stop rule: a failed precondition stops the run at once, a failed observation lets its scenario finish and then stops the run, because later scenarios build on the same document. `ENGINE=cef` runs scenarios 3, 4, 5 and 7 in CEF instead of WebView2. `target/debug/gate.exe all LOG [full|light|ui]` (crates/gate/src/all.rs, the Rust port of the former scripts/gate.sh) is the pre-merge gate: sequential stages, with progress and verdicts in `LOG` (a `GATE <stage> start` and `GATE <stage> exit=` line per stage, `GATE done` last) and each stage's output in `LOG.<step>.log` (`LOG.two-N.log` for the `gate two` runs). It starts one `--headless` instance on a throwaway `APPDATA` with one tab, polls `GetForegroundWindow` every 50 ms and logs each change (window, class, title, process), each window the instance and its engine host create, and each of their threads' own active window, then ends with `VERDICT foreground unchanged` or `VERDICT foreground taken by ...`. Whether a background process may take the foreground depends on the moment (refused while you are typing in another app, allowed when nothing has it or the foreground lock timed out), so `-Permissive` forces the worst case: an off-screen form takes the foreground first and opens it to every process (`AllowSetForegroundWindow(ASFW_ANY)`); it steals the foreground for the run. Found 2026-10-07: winit's default `SW_SHOW` activated the headless window, and the WebView2 host's window activated on its first `ShowWindow` and on `MoveFocus`; either took the foreground whenever allowed (once out of a fullscreen game). Now the headless window is created `with_active(false)` and the host window `WS_EX_NOACTIVATE`. `-Visible` runs a normal on-screen window (`--debug-commands`) instead: it must take the foreground and still have it at `QUIT`. Before the fix the WebView2 host took it from a normal window too, on every WebView2 tab start; after it, three of four `-Visible -Permissive` runs kept it, and in one the window lost it (to `msrdc`, 100 ms after the host's `MoveFocus`). Rechecked 2026-10-07 against a control host built without `MoveFocus`: with it, 9 of 10 visible runs (`-Visible`, `-Visible -Permissive`) kept the foreground through `QUIT`, holding it 4 to 12 s after the host's `MoveFocus` where that came early enough to see; without it, 9 of 9 kept it; headless `-Permissive` was unchanged in 3 of 3 each. The one loss went to a freshly spawned WSLg `msrdc` (its `wslhost.exe` started 6 s before) whose RemoteApp window took the foreground 1.3 s before the engine host even started, so `MoveFocus` played no part, and the original loss to `msrdc` was most likely the same. Without `MoveFocus` the host's thread never activates its window at all. `MoveFocus` stays.


**Engine setup for the gate** (each engine's host built and placed once; then `ENGINE=<name>` or `VIEWS=<name>` picks it for a stage, `VIEWS` winning when both are set, or `WITH_ENGINES` adds it to `gate all`). Run from the repo root, 2026-10-24:
- *Servo* (a cold build is about 33 minutes, a warm one seconds): `CARGO_TARGET_DIR=target-servo cargo build -j 6 -p manifold-view-servo`, then `target/debug/gate.exe sync-runtime-deps` (it puts Servo's DLLs beside the host in `target-servo/debug/`, where manifold runs it).
- *CEF* (needs the CEF download that `cef-dll-sys` makes): `cargo build -j 6 -p manifold-view-cef`, then `target/debug/gate.exe sync-runtime-deps` (it copies the host and runtime into `target/debug/cef-runtime/`).
- *WebKitGTK* (WSL Ubuntu with `webkit2gtk` and `xvfb`): `wsl.exe -d Ubuntu -- bash -lc 'cd /mnt/c/.../manifold && CARGO_TARGET_DIR=target-linux cargo build -j 6 -p manifold-view-webkitgtk'`, find the gateway with `wsl.exe -d Ubuntu -- ip route` (the default route's `via`), and run the stage with `SITE_HOST=<that ip>`; Windows Firewall must allow inbound for `manifold.exe` and `gate.exe`.
- Check one with `VIEWS=<servo|cef|webkit> gate page-text` (4-5 s); `trail` and `sleep` take `ENGINE=` / `VIEWS=` the same way.

**Building Servo on its own:** `CARGO_TARGET_DIR=target-servo cargo build -p manifold-view-servo` keeps its dependency tree out of `target/` so it can be deleted alone. Measured 2026-09-30: 3.9 GB for a full debug build (33 minutes at `-j 6`), almost all in `build/` (`mozjs_sys` 0.8 GB), so there is little to trim; `target-servo` is git-ignored. manifold runs the host from `target-servo/debug/` (it walks up from `manifold.exe`'s folder, ahead of any copy beside the exe), so nothing is copied into `target/`; run `target/debug/gate.exe sync-runtime-deps` after each Servo build for its DLLs (2026-10-29). Build Servo only there: a Servo host built into `target/` would run from beside `manifold.exe` with no DLLs placed for it, and its tabs fail to start.

Both scripts run `target/debug/manifold.exe` as it is, and `cargo check`/`test`/`clippy` don't rebuild it, so both refuse an exe older than any source it was built from (read from cargo's `manifold.d` dep-info; `gate fresh`, crates/gate/src/fresh.rs). The WebView2 host beside it (`manifold-view-webview2.exe`, read from its own `.d`) is judged the same way. Build with `cargo build -p manifold -p manifold-view-webview2` (`-p manifold` alone does not build the host), or set `ALLOW_STALE=1` to run the old one on purpose.

**Keyboard-shortcut reference popup**: `F1`, or a new `?` icon button next to Settings on both Tab and Graph toolbars, opens a centered popup listing every global shortcut `handle_global_shortcuts` handles (New Tab, Close Tab, Reopen Closed Tab, Duplicate, Next/Prev Tab, Quick Switcher, Tab/Graph toggle, New Group, Rename Group, Pin, Focus Address Bar, Find, Reload, Zoom in/out/reset, DevTools, and this popup itself) -- so a shortcut added over the session's course isn't only discoverable by reading the source. Static content, no staged state -- just an `Area`/`Frame` with a scrollable two-column `Grid` and a Close button. New `TOGGLESHORTCUTSHELP` debug command for headless parity. **Bug found and fixed while wiring up the button**: the first version passed `anchor_rect: None` to the shared `clicked_outside_popup` helper (see the click-outside dedup above) since a `?` button has no state-driven position to defer past -- but that meant the very click that opened the popup, still live in `ui.input()` the same frame, was itself seen as an "outside" click (correctly outside the popup's own rect, which the settings gear's button also is -- the reason it always passed its own rect there) and closed the popup back immediately. `F1` never showed the bug since a key press isn't a pointer click. Fixed by threading the button's own `Response::rect` through as `anchor_rect`, same as every other anchored popup already does. Verified live: `F1` toggled the popup open and closed repeatedly; separately confirmed the button now does too, matching the gear icon's own behavior.
