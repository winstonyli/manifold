# Manifold

A browser where each tab can run on a different rendering engine — Blink (via CEF), Servo, WebKit (via WebKitGTK), or Blink again (via Microsoft Edge WebView2) — and the engine backing a tab can be swapped live without closing it.

Status: M0–M5 complete — single-engine tabs on Servo/CEF/WebKit, live engine swap, a real chrome, crash recovery, and multiple tabs shown as a force-directed graph (peek to preview, click to focus), all verified end-to-end. Full milestone plan: `C:\Users\Winston Li\.claude\plans\stateless-napping-sunset.md`. **M6 (WebView2, off-plan):** a fourth engine, native Windows API rather than a same-machine child of a separate SDK/runtime checkout — frame capture (`Windows.Graphics.Capture`), navigation, favicon, zoom, click/scroll/drag-selection input (real OS-level `SendMouseInput` via Composition hosting; keyboard/text entry stays CDP/script-driven — see Known limitations), taskbar-hiding for its off-screen host window, and popup interception (`target=_blank`/`window.open()`/ctrl+click) are all implemented and verified live.

## Architecture

```
manifold            winit + wgpu compositor, process manager, swap logic
manifold-engine-servo     Servo, same-machine child process (named pipe + shared memory)
manifold-engine-cef       CEF (Blink), same-machine child process (named pipe + shared memory)
manifold-engine-webkit    WebKitGTK, hosted inside WSL2 (TCP transport, no shared memory across the VM boundary)
manifold-engine-webview2  Microsoft Edge WebView2 (Blink), same-machine child process (named pipe + shared memory)
ipc-protocol          shared message types + both transports
```

Only `manifold-engine-webkit` is Linux-only (no Windows WebKit embedding exists); everything else builds natively on Windows.

  (Rust/cargo must also be installed inside that WSL2 distro, separately from the Windows-side toolchain.)

## Building

**Windows-side crates** (`manifold`, `manifold-engine-servo`, `manifold-engine-cef`, `manifold-engine-webview2`) — from a regular shell at the repo root:

```bash
PATH=$(echo "$PATH" | tr ':' '\n' | grep -v -F "depot_tools" | tr '\n' ':') cargo build -p manifold -p manifold-engine-servo -p manifold-engine-cef -p manifold-engine-webview2
```

The `PATH` filtering is only needed if `depot_tools` is on your PATH; harmless otherwise.

**WebKit engine-host** — built *inside* WSL2, into its own target directory (it can't share `target/` with the Windows build — different OS, different toolchain):

```bash
wsl.exe -d Ubuntu -- bash -c 'cd "/mnt/c/Users/<you>/Documents/GitHub/manifold" && CARGO_TARGET_DIR=target-linux cargo build -p manifold-engine-webkit'
```

Adjust the path for wherever this repo actually lives on your machine (WSL2 sees your Windows drives under `/mnt/c/...`).

### Runtime-file placement (required after every build)

Cargo doesn't do this itself — see the `TODO` in `crates/manifold/src/process_manager.rs`'s `engine_binary_path`. Both CEF and Servo need extra files placed next to their binaries after each build, because they'd otherwise collide (both ship an ANGLE `libEGL.dll`/`libGLESv2.dll` under the same filenames, and Windows resolves an implicit DLL dependency from the loading EXE's own directory first — whichever copy landed there last silently wins for *both* engines).

`manifold-engine-webview2` doesn't need this: WebView2Loader is a single small loader, statically linked by the `webview2-com` crate (or at worst one lone DLL) — none of the ANGLE-style same-filename collision the other two have.

Run this after every build that touches `manifold-engine-servo` or `manifold-engine-cef`:
```bash
bash scripts/sync-runtime-deps.sh
```
It finds Servo's ANGLE DLLs and CEF's runtime under `target/debug/build/{mozangle,cef-dll-sys}-*/`, `cmp`s each against the copy already in place, and only recopies what's actually stale (safe to run any time — a no-op if nothing changed). Not a build.rs: a build script only sees its own crate's `OUT_DIR`, not a sibling crate's, and there's no reliable cross-crate coordination here without those upstream crates cooperating (they don't) — a plain script is simpler and more honest than fighting Cargo's model.

Why this needs a script at all rather than a one-time manual copy: Cargo has regenerated the `mozangle-<hash>`/`cef-dll-sys-<hash>` fingerprint directory these live under even on a rebuild that touched neither `Cargo.toml` nor `Cargo.lock`, leaving a stale copy in place that keeps working right up until it silently doesn't (Servo: panics with `egl function was not loaded`; CEF: silently runs stale code). The script picks the candidate whose own output *file* has the newest mtime, not the containing directory's — a build touches every candidate directory's own fingerprint bookkeeping on every invocation regardless of whether it actually recompiled that crate, which can leave several near-identical timestamps and make directory-mtime-based "newest" ambiguous.

A rebuild also tends to leave the *previous* hash's directory behind alongside the new one (Cargo doesn't clean up an old fingerprint just because it's no longer used) — these accumulate across sessions and are a repeat cause of this project filling the disk. Safe to prune anything under `target/debug/build/{mozangle,cef-dll-sys}-*` except whichever one `scripts/sync-runtime-deps.sh` just used — re-run the script afterward to confirm nothing needed recopying. Getting this wrong (deleting the wrong one) just means the next build regenerates whatever's missing, not silent breakage — but it's wasted rebuild time.

## Running

**Superseded below -- kept for the debugging trail, not as current advice.** This section originally said to always use `cargo build --release`, because a debug build of a single idle tab ran at ~13-16fps (~60-80ms/frame) against release's smooth ~60fps (~16.8ms) -- a ~4-5x gap traced to `GpuState::upload_frame`: a brand-new GPU texture allocated from scratch on every uploaded frame, plus a CPU-side pixel format-conversion/downscale feeding the thumbnail, both of which a debug build pays full, unoptimized price for. Investigated (not assumed) via temporary frame-timing instrumentation, and confirmed *not* pan-specific along the way -- a control test holding a background-pan drag with zero movement measured the same frame time as sitting fully idle. Both root causes are now fixed directly in the app's own code (see this file's own changelog: the texture-reuse fix and the GPU-downscale fix, both below) rather than left as a "just build differently" workaround. Re-running the identical idle test after both fixes landed: debug dropped to ~16.7ms, matching release (~16.7ms, unchanged) almost exactly -- the specific gap this note used to warn about no longer exists.

```bash
target/debug/manifold.exe
```

That said, this doesn't make debug and release *generally* equivalent -- Rust's own optimization gap is real for any other CPU-bound path this investigation didn't specifically target, just no longer the dramatic, workload-defining one `upload_frame` used to be. `cargo build --release` remains worth reaching for if something *else* feels slow and profiling points at unoptimized CPU work, same as in any Rust project:

```bash
target/release/manifold.exe
```

Starts on **Graph view**, with one root tab (Servo, loading `https://example.com`) already spawned and focused — click its node to enter Tab view. The graph is the primary view for managing multiple tabs:

- **Graph view**: every tab is a node (its last frame as a downscaled thumbnail, favicon, title, current engine) connected by an edge to the tab it was opened from. Hover a node to peek an enlarged preview without changing focus; click a node to focus it (switches to Tab view); drag a node to reposition it — edges settle to a rest length of 320 points, up from 180, so sibling nodes don't crowd/overlap each other at equilibrium; the small "x" at a node's corner closes that tab, reparenting its children to its own parent; a small circle at a node's bottom-left corner pins/unpins it (filled = pinned) — a pinned node is excluded from the layout entirely (the same exclusion a node currently being dragged already gets in `graph_layout::step`), so a future settle never moves it, though it still exerts its own spring/repulsion force on its unpinned neighbors when one runs. Not persisted to `session.json` — resets to unpinned on restart.

**`Escape` dismisses a hover-peek preview early**: previously the only way to close a peek was moving the pointer away; `Escape` now does it too, without needing the pointer to move at all. Can't just clear `hovered` directly -- Graph view's Escape check runs before the per-node loop that re-detects `response.hovered()` each frame, so clearing it there would just get silently overwritten later the same frame by the pointer still sitting over the node. Instead a new `peek_suppressed` field is set to the currently-hovered id, checked by the peek-drawing code to skip rendering for that specific id; it's cleared automatically the moment `hovered` changes to anything else, so hovering away and back (or hovering a different node) always shows a fresh peek. New headless `DISMISSPEEK` debug command, since Graph view's own `Escape` handling reads real key state the existing `ESCAPE` debug command doesn't reach (that one's Tab-view-only). Verified live: hovered a node (peek visible), sent `DISMISSPEEK` with the pointer never moving and confirmed the peek disappeared while the node's own hover state (its "x" close button) stayed visible, then moved away and back and confirmed the peek reappeared.

**Fixed (layout model changed):** the force-directed layout used to run continuously, every frame, for as long as any node at the current level existed — which meant every unpinned node, *including whatever a drag was currently aimed at*, kept reacting to repulsion in real time. Confirmed live while building the drag-a-tab-onto-another-tab feature below: a slow, multi-step drag toward a target let that target's own repulsion push it away from the incoming drag, so the two visibly chased each other rather than meeting, and only a single fast cursor jump (no intermediate positions for the target to react to) reliably landed a drop. The layout now runs only as a one-shot settle burst (90 iterations at a fixed 1/60s step, comfortably past the convergence a full continuous run needed) whenever the visible node count at the current level actually changes (a spawn, a close, a group forming) — not every frame — and is skipped entirely while any drag is in progress, so nothing moves on its own while the user is trying to point at it. New/remaining nodes still auto-spread apart from each other via the settle burst; a node repositioned by hand simply stays exactly there afterward, with no ongoing correction if it now overlaps a sibling — the accepted tradeoff for a drop target that never runs away. Verified live: a slow, multi-step drag that previously required a single fast jump to land now completes reliably, with the target visibly staying in place as the drag approaches; a fresh two-node graph still auto-separates to the same equilibrium spacing as before. "+ New Tab" opens a child of whichever tab is currently focused (or a new root if none is). Drag empty background to pan, scroll to zoom (centered on the cursor); the zoom chip's Fit button (formerly "Reset View") fits every node currently visible at the current level (tabs/downloads, plus group cards at the top level) into frame — each node's own card bounds (not just its center point) plus a flat margin, rather than always the same fixed world-space rect regardless of how many nodes exist or how far one's drifted — falling back to a fixed default-sized rect only when there's nothing to fit (an empty group, or before any tab has spawned). The chip also has −/+ buttons (×1.25 per click, clamped to the 15%–300% zoom range) and a clickable percentage readout that resets to 100% keeping the current pan. Entering/leaving a group reuses the same fit instead of the old fixed framing too, so a group's own members are framed on arrival rather than assuming they happen to sit near world center. Verified live: dragged a child node far from its parent, clicked Reset View, and the resulting frame centered on and fully contained both nodes with even margin on every side, re-run with a third tab present to confirm it scales to more than two nodes.

Graph view's default zoom is closer-in than a raw 1:1 scene (the scene's default world-space extent shrunk from 1600×1100 to 900×620) so nodes read larger on first open instead of needing an immediate manual zoom-in. **Fixed:** plain scroll used to pan (egui's `Scene` container hardcodes ctrl+scroll as its zoom gesture and plain scroll as pan, not configurable via its own builder), leaving zoom stuck behind a modifier and pan doubled up with the drag gesture above. Verified live: zoomed out until a card's thumbnail shrank to a fraction of its original size while its favicon, pin dot, close button, and title text stayed visibly the same pixel size as at 100% zoom. **Fixed (properly this time):** that first pass sized text the same `* inv_zoom` way as the vector shapes, which fixed the on-screen *size* but not *sharpness* — egui rasterizes each glyph into its font atlas at the requested world-space size, so a small `inv_zoom` (high zoom-in) asked for a tiny atlas glyph that `Scene`'s transform then visibly blurred back up to size. Arrow keys move a keyboard focus highlight between tab nodes at the current level without touching the mouse — reuses the same `focused` field the ACCENT border already highlights and every other "act on the focused tab" path already reads (`Ctrl+W`, "+ New Tab"'s parent, Enter-to-open), so a keyboard-selected node behaves exactly like a clicked one. Enter opens whatever it's currently on, the same as clicking its card. Gated off while the settings popup or a group rename field is open, so arrow keys still do their normal job there. Verified live: two `GRAPHLEFT`s correctly walked the highlight two nodes leftward (not straight to the far one), `GRAPHRIGHT` correctly stepped back to the nearer neighbor rather than the original node, and `GRAPHOPEN` opened the highlighted node into a real, stable Tab view. Switching between Graph and Tab view (clicking a node, or the "Graph"/Escape button) animates as a 220ms shrink/expand: the transitioning tab's live content morphs between full-window size (Tab view) and its graph node's thumbnail-sized rect (Graph view), smoothstep-eased, rather than cutting instantly. This reuses the exact same world→screen transform the graph's own `Scene` container uses to place nodes (replicated by hand in `App::graph_world_to_screen_transform`, matching egui 0.36's internal `fit_to_rect_in_scene` formula — not exposed publicly, so not a dependency, just the same math) so the animated rect lands exactly on the real node position, not an approximation. During the animation the app stays logically in Graph view (chrome, physics tick, node layout all keep running underneath) with only the one transitioning tab's content quad drawn at an interpolated viewport rect, layered *on top of* the graph (not underneath it) so the shrinking/expanding content is never hidden behind other nodes/edges as it animates. **Fixed:** because Graph view's own node-click handling keeps running as that backdrop for the whole 220ms, clicking a node again (the same one, or a different one) before the first click's expand animation finished used to retarget `App::transition` mid-flight — the animation would jump partway through to the new node, and `focus_tab` would hide the first tab's still-animating content out from under it. `start_transition_to_tab` now ignores the click entirely while a `Transition` is already running, so extra clicks during the animation are just dropped rather than corrupting it.
**Tab groups**: "+ New Group" (top level only) creates an empty container node; dragging a tab card onto a group's card joins it, hiding it from the top level. Dragging one ungrouped tab onto *another* ungrouped tab (not a group card) creates a new group containing both, named the same "Group N" way "+ New Group" names one — the two tabs are the only kind of node an ungrouped tab can ever land on at the top level (a group's own members only render one level deep, inside that group's own subgraph, so an ungrouped tab and an already-grouped one never coexist on screen as drop targets for each other). **Live download progress (byte-level, real native APIs)**: a download's own graph node/popup row used to only appear once the file was already fully saved (`DownloadNode`'s own doc comment used to call it "a **completed** download" -- there was no in-progress representation at all, checked while scoping this feature and confirmed the only IPC message that existed anywhere was `DownloadCompleted`). CEF and WebKit build clean against the exact same handler pattern `find_handler.rs`/WebKitGTK's own find/favicon code already use successfully, but a live click-triggered download wasn't reproduced for either in the time available this session (CEF's real native mouse-injection input mechanism needs different on-screen coordinates than WebView2/WebKit's script-driven clicks, and a coordinate mismatch — not necessarily the download code itself — is the most likely reason the test click never landed on the link). Servo has no download hook in its embedding API at all, same per-engine gap as find-in-page and DevTools.

A completed download also shows up as its own node in Graph view, edged to the tab it came from — same force-directed layout/edge machinery `TabNode`s already use (`graph_layout::step` treats tabs and downloads as one flat id space), just a smaller card with a filename instead of a live thumbnail (no engine process/content behind it). Click a download node to open its containing folder with the file pre-selected (`explorer.exe /select,<path>`) — a WebKit-sourced path is translated from its WSL2-side form to the `\\wsl.localhost\Ubuntu\...` UNC path Explorer can actually browse first. The "x" only forgets the node, never deletes the file. Closing a download's parent tab reparents it to that tab's own parent, the same rule `close_tab` already applies to child tabs; download nodes are session-only (not written to `session.json`) since the file itself already exists on disk regardless of whether the node survives a restart. Verified live on WebView2: a real downloaded file showed up as a node with a correct edge to its source tab, right where the download-completion toast paragraph above's own debug-logged `DownloadCompleted` event said it would.

Each graph node shows a small green dot at its top-right corner while that tab's page is producing audio — a plain painter-drawn circle rather than a speaker glyph (several Unicode symbol glyphs, `▲`/`▼`/`✕` among them, are confirmed elsewhere in this app to render as empty boxes in whatever font it actually has glyphs for). WebView2 (`ICoreWebView2_8::IsDocumentPlayingAudio`/`add_IsDocumentPlayingAudioChanged`, needing `webkit2gtk`'s `v2_8` Cargo feature — bumped up from `v2_6`) and WebKitGTK (`WebView::is_playing_audio`/its `is-playing-audio` GObject notify) both expose this as a real *passive* read of state the engine already tracks, no different in kind from reading a tab's `title`. CEF has no such API short of registering an `AudioHandler`, which takes over delivering every raw PCM audio packet to the app instead of playing it through normal OS audio output — a real audio-routing feature, not a passive read, and a much bigger and riskier change than a tab icon warrants (get it wrong and CEF tabs go silent). **Later session pass: CEF sends this too now, by a different route** -- see the dedicated writeup further down. Servo's embedding API has no such property at all. **Not live-verified this session**: this project's synthetic click input (`el.click()` via `ExecuteScript`/`nav_action` — see Known limitations) doesn't carry the "sticky user activation" browsers require before an autoplay-gated API like `AudioContext` will actually start producing sound, so a real audio stream could never be triggered to confirm the indicator turns on; the API usage itself is a single documented property read, the same shape already verified working for favicon/find on both engines.

**Audio indicator upgraded to a tiny animated waveform**: the plain green dot above now only shows while muted (a static red dot, since nothing is actually playing to animate); while actually playing it's replaced by a 3-bar waveform, still painter-drawn rects rather than a speaker/equalizer glyph. Animated off `std::time::SystemTime::now()` rather than egui's own `ui.input(|i| i.time)` — **found live**, not assumed: driving the indicator through a temporary `TESTSETAUDIO` debug command (set `audio_playing` on the focused tab directly, removed after verifying, same disposable-hook pattern used elsewhere in this project) and comparing cropped/upscaled screenshots taken seconds apart showed `ui.input`'s own time reading as completely frozen across separate headless `SCREENSHOT`-triggered redraws, even though each redraw was demonstrably fresh (the newly-set `audio_playing` state itself only ever appears after one). Switching the animation's clock to a plain OS `SystemTime` read sidesteps whatever that staleness is and was confirmed to tick correctly the same way. This app already requests a redraw unconditionally at the end of every frame, so the animation needs no extra repaint request to keep running on its own. Verified live: cropped/upscaled screenshots of the indicator corner showed three distinct bars of different heights (not a dot), and a second capture two seconds later showed measurably different bar heights.

A "Muted" toggle button sits in Tab view's toolbar (right after the engine picker) — `selectable_label`'s pressed look when active, no speaker glyph risked. This is host-initiated (unlike the passive audio-playing read above), so there's no `EngineToHost` reply: `manifold` tracks a per-tab `muted` flag itself and sends `HostToEngine::SetMuted { muted }` on click. WebView2 (`ICoreWebView2_8::SetIsMuted` — the exact same interface `IsDocumentPlayingAudio` already uses) and WebKitGTK (`WebView::set_is_muted`, needing the `webkit2gtk` Cargo feature bumped to `v2_30`) both have a real native mute API; CEF also mutes now (see the dedicated writeup further down), and Servo has no audio control at all — silent no-op there only. Verified live on WebView2: clicking the button called `ICoreWebView2_8::SetIsMuted(true)` (confirmed `Ok`) and a follow-up `IsMuted` read-back on the same interface correctly returned `true` (temporary debug logging, since removed). WebKit's wiring uses the identical `WebViewExt::set_is_muted` pattern already proven for `set_zoom_level` in the same file, and builds clean, but wasn't independently re-verified live this session — this project's own documented WebKit-headless-test flakiness (see below) made every attempted repro this session fail to even reach a spawned tab within a generous wait, a spawn-timing problem rather than anything specific to this change.

`Ctrl+F`'s find bar (top-right of Tab view) searches the focused tab's real page content as you type, via each engine's own native find API — `ICoreWebView2Find`/CEF's `BrowserHost::find`/WebKitGTK's `WebKitFindController` all highlight matches directly in the page and report a live match count; Prev/Next (or Enter/Shift+Enter) step through them, the "Aa" toggle switches case-sensitivity (re-searching immediately, resets to off on a fresh search), Escape or the bar's own close button ends the search. Verified live on CEF and WebView2 (highlighting, match count, active-match tracking, and the case-sensitivity toggle all correct — e.g. searching "banana" against a page with one capitalized "Banana" and two lowercase drops the count from 3 to 2 with the toggle on); WebKit's wiring is written against the same `WebKitFindController` API this project's favicon code already uses successfully, but not build/run-verified this session (WSL2 itself failed to start in this environment — a VM-creation error unrelated to this change). Servo has no find-in-page API in its embedding surface at all — the bar still opens on a Servo tab (confirmed live: no crash, no hang) but never shows a match count, same per-engine gap as popup interception.

Tab view's toolbar has a "Screenshot" button (next to "Muted") that saves the whole composited window — chrome and content, not just the page — as a PNG to `%USERPROFILE%\Pictures\manifold-<unix-seconds>.png`, then shows the same "Saved <path>" toast the download feature uses (the two now share one `save_toast` field/`build_save_toast` renderer rather than a download-specific one). No save-as dialog, same "pick the obvious default" posture as everywhere else this project saves a file. This is the exact same capture path the headless `SCREENSHOT` debug command already uses (`GpuState::render`'s `screenshot_path` parameter, a second GPU render into a plain `COPY_SRC` texture then read back) — the button just supplies a real default path instead of a test-provided one, engine-agnostic since it works off the already-composited frame rather than anything engine-specific. Verified live: clicking it produced a real, correctly-rendered PNG of the page on disk, with the toast shown in the same screenshot.

Only the focused tab ever actually renders — every other tab's engine-host process stays alive (so its page keeps running, JS timers and all) but stops producing frames until it's focused again; its node just shows the last frame it produced. New tabs are created via "+ New Tab" (or `Ctrl+T`), or automatically as a child node when a page opens one itself (`target=_blank`/`window.open`/ctrl+click) — CEF, WebKit, and WebView2 all intercept and forward these; Servo does not (falls back to its own unhandled-popup default), see Known limitations.

If an engine-host process dies (crashes, or is killed) — focused or not — the tab automatically respawns the same engine at its last-known URL, keeping its place in the graph.

The URL carries over on an engine swap; other state (cookies, scroll position, etc.) does not — a known v1 limitation, not a bug.

The whole tab graph (which tabs, their url/engine/graph position, who opened whom, which tab is focused, which view is active) is saved to `%APPDATA%\manifold\session.json` on every change that matters (a tab spawns, closes, navigates, or focus/view changes) and restored at the next launch, instead of always starting over at one root tab on the home page. A missing or corrupt session file just falls back to that original single-root-tab startup; a corrupt one is first renamed to `session.unreadable-<unix-seconds>.json` and named in a toast, so the next save can't overwrite it. Like an engine swap, only the graph's shape is portable across a restart — a restored tab is a fresh navigation to its last known URL, not a resumed one (no cookies/localStorage/scroll position).

Each engine-host writes its own log to `%TEMP%\manifold-<tab_id>.log`.

**Image view**: clicking an image card maximizes it into Item view (the same animated expand/shrink a tab card uses; Escape or the "Graph" button returns). The toolbar is the shared Item toolbar frame -- "Graph" at the left, the Help/Settings chip at the right -- with the image's own content between: its filename and pixel size, a zoom chip (−, percentage, +, Fit; the same chip the Graph toolbar uses), and Open Containing Folder / Copy Path. The image opens at Fit (contained, never above 100%); the mouse wheel zooms about the cursor (10%–1600%), dragging pans (never past the image's edges), and `Ctrl+=`/`Ctrl+-`/`Ctrl+0` zoom it. A maximized image is restored on relaunch (at Fit). Tab-only shortcuts (Ctrl+W, F5, …) keep acting on the last focused tab, as they do from Graph view.

## Headless mode (automated testing)

```bash
target/debug/manifold.exe --headless
```

Runs the same app, but the window is positioned far off-screen (not `--visible(false)` — a genuinely invisible window's swapchain never successfully acquires a frame on Windows, DWM permanently reports it occluded; an off-screen-but-visible window keeps rendering normally while never overlapping the user's actual screen) and driven entirely by a text-command protocol read from stdin, one command per line, instead of real OS input. This exists so live GUI testing of this app doesn't have to fight Windows' foreground-lock (`SetForegroundWindow` can be silently refused while the user is active on their own machine — see project memory) or contend visually with whatever the user is doing.

Commands:
- `MOUSEMOVE <x> <y>`, `MOUSEDOWN <x> <y> [left|right|middle]`, `MOUSEUP <x> <y> [left|right|middle]`, `CLICK <x> <y> [left|right|middle]` — dispatched as genuine synthetic `winit::event::WindowEvent`s, not a logic bypass, so they exercise real egui hit-testing exactly like real input would.
- `SCROLL <x> <y> <delta_x> <delta_y>`
- `ADDRESSBAR <text>` — sets the address bar's text and focus state directly and recomputes suggestions (headless has no way to synthesize a real click-driven egui focus transfer, since `winit::event::KeyEvent` has no public constructor outside the winit crate — see `debug_control`'s doc comment).
- `ENTER` — navigates using the address bar's current text.
- `ESCAPE` — dismisses the suggestion dropdown, or leaves Item view (a maximized tab or image) for Graph view if none is showing.
- `ARROWDOWN` / `ARROWUP` — moves the address-bar dropdown's highlighted row (wrapping at both ends); a following `ENTER` accepts it.
- `TYPE <text>` — sends each character to the focused tab's page (not the address bar).
- `KEYPAGE <name>` — sends a KeyDown+KeyUp of the named key (`Enter`, `Backspace`, `ArrowLeft`, a single letter/digit, etc.) to the focused tab's page.
- `NEWTAB` / `CLOSETAB` / `FOCUSADDRESS` / `NEXTTAB` / `PREVTAB` — the `Ctrl+T`/`Ctrl+W`/`Ctrl+L`/`Ctrl+Tab`/`Ctrl+Shift+Tab` shortcuts' exact same effect, called directly (same rationale as `TYPE`/`KEYPAGE`: no public way to synthesize a real `Ctrl`-chorded `KeyboardInput`). `FOCUSADDRESS` is the one command among these that isn't instant — it drives a real `egui::Response::request_focus()`, which (immediate-mode) only takes visible effect starting the *next* frame, so it also forces a redraw itself rather than relying on some later, unrelated command to eventually trigger one.
- `SCREENSHOT <path>` — saves the next composited frame (chrome, any open dropdown, and content) as a PNG, read back directly from the GPU rather than `PrintWindow`/`CopyFromScreen` (see project memory's gotchas on GDI-handle exhaustion and foreground-lock unreliability with that approach).
- `RESIZE <width> <height>`
- `SETVISIBLE <true|false>` — sends `SetVisible` directly to the focused tab, bypassing `focus_tab`/`leave_to_graph`'s own visibility changes (which always come bundled with a `Resize`, since Tab vs. Graph view's chrome heights differ). For testing the background-tab suspend/resume path in isolation.
- `QUIT` — exits cleanly. Also sent automatically on stdin EOF, so a driving script that closes its write end doesn't leave the process hanging.

`scripts/headless-smoke-test.sh` is a runnable example (and a real regression smoke test): drives the address-bar autocomplete flow end to end via a bash `coproc` and asserts each screenshot was actually produced and isn't suspiciously small, plus app state read back through `EXPORTSESSION` (whether it's in Tab view, the focused tab's URL). That's not visual-regression testing, but it catches wrong behavior as well as crashes; the checks allow for DuckDuckGo's suggestion order changing between runs. It runs in its own throwaway `APPDATA` profile (starting from just the root tab) and leaves other running manifold windows alone. Run it after `cargo build -p manifold`. Note for anything driving this from Git Bash/MSYS: a `SCREENSHOT` path travels over stdin, not argv, so it's not auto-translated from a POSIX path (`/c/Users/...`) the way a command-line argument to a spawned native exe would be — convert with `cygpath -w` first.

`scripts/drive.sh <commands-file>` runs one session from a file of commands, in a fresh isolated `APPDATA` (so the real `%APPDATA%\manifold` is never touched), deleted afterwards unless `KEEP_APPDATA=1`. `SEED=<dir>` copies that directory's `*.json` into the profile first (e.g. a hand-made `session.json`), and `VISIBLE=1` uses a real window instead of `--headless`. In the file, `{repo}` becomes the repo root as a Windows path (`SCREENSHOT {repo}\target\shots\a.png`), `sleep N` is sent as the app's in-order `SLEEP`, and a line starting with `!` runs in bash (not in step with the app; wait for a file an `EXPORTSESSION` writes to sync). The script's header has the details.

**Keyboard-shortcut reference popup**: `F1`, or a new `?` icon button next to Settings on both Tab and Graph toolbars, opens a centered popup listing every global shortcut `handle_global_shortcuts` handles (New Tab, Close Tab, Reopen Closed Tab, Duplicate, Next/Prev Tab, Quick Switcher, Tab/Graph toggle, New Group, Rename Group, Pin, Focus Address Bar, Find, Reload, Zoom in/out/reset, DevTools, and this popup itself) -- so a shortcut added over the session's course isn't only discoverable by reading the source. Static content, no staged state -- just an `Area`/`Frame` with a scrollable two-column `Grid` and a Close button. New `TOGGLESHORTCUTSHELP` debug command for headless parity. **Bug found and fixed while wiring up the button**: the first version passed `anchor_rect: None` to the shared `clicked_outside_popup` helper (see the click-outside dedup above) since a `?` button has no state-driven position to defer past -- but that meant the very click that opened the popup, still live in `ui.input()` the same frame, was itself seen as an "outside" click (correctly outside the popup's own rect, which the settings gear's button also is -- the reason it always passed its own rect there) and closed the popup back immediately. `F1` never showed the bug since a key press isn't a pointer click. Fixed by threading the button's own `Response::rect` through as `anchor_rect`, same as every other anchored popup already does. Verified live: `F1` toggled the popup open and closed repeatedly; separately confirmed the button now does too, matching the gear icon's own behavior.

## Known limitations

- **Fixed:** "extreme lag on startup," reported live by a user, longstanding and unrelated to any recent change. Root-caused via temporary per-phase timing instrumentation through `main()`/`resumed()`/`GpuState::new` (removed after measuring): of a ~1.3-1.5s total time from process start to the first real frame, `wgpu::Instance::new()` alone accounted for ~640ms (over 40%) -- `wgpu::InstanceDescriptor::new_without_display_handle()`'s own default `backends` is `Backends::all()`, which on Windows also loads/probes the `GL` (ANGLE-backed) secondary tier this app never ends up using (`adapter.get_info()` confirmed it always lands on Vulkan or DX12 in practice). Fixed by explicitly restricting `backends` to `wgpu::Backends::PRIMARY` (Vulkan/Metal/DX12/WebGPU only) -- wgpu's own recommended set for exactly this "skip the legacy fallback tier" reason. Verified live: `Instance::new()` dropped to ~130-160ms across two repeated timing runs (from a consistent ~640ms baseline), with the same adapter (AMD Radeon RX 9060 XT via Vulkan) still selected either way -- no behavior change, purely faster. Request-adapter/request-device/pipeline-creation (shader compile) remain real, likely-irreducible costs of talking to the GPU driver and weren't touched; a `wgpu::PipelineCache` to skip shader recompilation across runs is a possible future win but out of scope for this fix.
- **Fixed:** the gear-icon Settings dropdown overflowed off the bottom of a small window, reported live by a user. Root cause: it was a fixed-position `Area` with no `ScrollArea` and unbounded height (grows with the saved-sessions list), only ever anchored below the gear button -- nothing clamped its height to the window's own. Fixed by turning it into a real `ViewMode::Settings` page instead of a popup: a top toolbar (Back button, title) plus a window-filling `ScrollArea`, so height is never an issue regardless of window size or list length. The gear button on both Tab and Graph toolbars now calls `toggle_settings_page` (enter from whichever view was showing, remembered in `settings_return_view`; a second click, `Escape`, or `Ctrl+G` returns to it) instead of opening the old popup. Content is left-aligned with a capped 480pt width (not centered -- tried centered first, changed on request) so long lines stay readable without stretching across a wide window. Verified live by the user directly (not this session's own automated testing, held off on per the user's own request): opened the page, requested the layout be left-aligned instead of centered (applied, see the 16pt-inset `Frame` wrapper around the content).
- **Fixed:** some headings/labels (`.strong()` text -- "Settings", "Sessions", "Bookmarks" section headers among them) rendered black on this app's own always-dark backgrounds, reported live by a user. Root cause: `apply_style`'s `ctx.all_styles_mut` only overrode specific widget-state fields on top of *whichever* base preset (`egui::Visuals::dark()`/`Visuals::light()`) egui had already loaded into that style slot; under a light OS/window theme, every field the function didn't explicitly touch -- including `.strong()` text color -- kept the light preset's own near-black default, invisible against `BG`/`TOOLBAR_FILL`/etc., which are forced dark unconditionally regardless of OS theme. Fixed by resetting `style.visuals = egui::Visuals::dark()` for both style slots before applying this app's own cosmetic overrides, so every untouched field starts from a coherent dark-appropriate default no matter which theme the OS reports. Verified live in this dev environment's own (already-dark) OS theme that headings still render correctly post-fix (light gray/white, clearly legible); the light-OS-theme trigger path itself wasn't independently reproduced, since nothing in this app's headless protocol can force winit to report a specific OS theme. **Recurred, different root cause, fixed:** "Settings" (and every other `.strong()` heading) still rendered black afterward, reported live again. Real cause this time: `RichText::strong()`'s color comes from `Visuals::strong_text_color()`, which egui defines as `widgets.active.text_color()` -- and `apply_style` deliberately sets that field to `Color32::BLACK`, needed for pressed/selected-button text to stay readable against the `ACCENT`-colored fill those states use. Headings aren't drawn on an `ACCENT` background, so they inherited black-on-dark from the same field for an unrelated reason. Fixed at each of the six `.strong()` call sites (`Settings`/`Sessions`/`Bookmarks`/`Import Session` popup headers, the bookmarks-folder bold header, and the new Keyboard Shortcuts popup's own title) with an explicit `.color(TEXT_PRIMARY)`, leaving `widgets.active`'s black untouched since pressed/selected buttons still need it. Verified live: all reported headings confirmed legible after rebuild.
- Session state (cookies, localStorage, IndexedDB) is not portable across an engine swap — only the URL carries over.
- **Fixed:** spawning a WebKit tab used to be able to freeze the entire app (unresponsive to all input, including headless-mode commands) for anywhere from sub-second to multiple hours. Two root causes, both hit on every WebKit spawn: (1) `ipc-protocol`'s `accept_remote()` called a plain, unbounded `TcpListener::accept()` on the main event-loop thread, so a slow WSL2/Xvfb/GTK boot blocked everything, not just that tab — fixed with a bounded 45s connect timeout that fails cleanly into the existing spawn-error UI path instead of hanging. (2) On tab close/crash-recovery, `Drop for EngineTab` force-killed the WebKit case's `wsl.exe` relay with zero grace period — that only kills the Windows-side process, not the actual Linux-side tree (Xvfb, GTK, the engine-host binary itself), leaving orphans running indefinitely; fixed by waiting up to 3s for a graceful WSL2-side exit first. The same unbounded-`accept()` pattern also existed in `accept_local_pair` (Servo/CEF's same-machine spawn) — lower risk since there's no cold-VM-boot equivalent, but hardened the same way regardless (a 10s bound, much shorter than WebKit's 45s since a same-machine child that hasn't connected within a few seconds has failed, not merely booted slowly). **Fixed (follow-up):** the `Drop for EngineTab` fix above only runs on manifold's own clean exit path — it never fires at all when manifold.exe itself is force-killed (`taskkill /F`, a crash) rather than exited normally, since no Rust destructor runs on that kind of process death. In that case, `manifold-engine-webkit`'s main loop kept polling GTK, capturing frames, and silently re-attempting now-dead sends forever — confirmed live, ~45% CPU indefinitely, wholly orphaned (no Windows-side process left to tear it down). Root cause: its reader thread already detected the dead control socket (Windows still closes the TCP connection on process death regardless of Drop, so `recv` reliably got an `UnexpectedEof`) but only broke its own loop silently instead of telling the main loop to exit. Fixed by having that `Err` path synthesize a `Shutdown` into the same channel the real message uses, reusing the existing clean-exit code path — see `manifold-engine-webkit/src/main.rs`'s reader thread. Only covers a parent that's actually gone (socket closed by the OS), not one merely hung-but-alive with the socket still open — no `Err` would fire in that case.
- **Fixed:** a headless `ENTER`/`ESCAPE`/`ARROWDOWN`/`ARROWUP` command immediately followed by `QUIT` with no delay between them (e.g. a fast test script) could exit the app before the earlier command was ever consumed, silently dropping it — `DebugCommand::Quit` used to call `event_loop.exit()` synchronously with no guarantee any frame ran first to process the pending flag. Fixed by deferring the exit one frame (`quit_after_next_redraw`) whenever a pending debug flag is still set when `QUIT` arrives, so the normal frame that would have consumed it gets to run first; a plain `QUIT` with nothing pending still exits immediately as before. Verified live via the exact back-to-back `ENTER`+`QUIT` sequence (temporary tracing confirmed the deferred path engages only when it should). **Same gap found and fixed for `SCREENSHOT`**: a `SCREENSHOT` immediately followed by `QUIT` had the identical problem (`pending_screenshot` is only consumed inside a `RedrawRequested`) — found live while testing a WebKit root-tab spawn, whose own cold-start delay made the race far more likely to actually trigger (a burst of queued stdin commands processed back-to-back the instant the blocking spawn call returns). `quit_after_next_redraw`'s trigger condition now also checks `pending_screenshot.is_some()`.
- **Fixed:** a headless `ENTER`/`ESCAPE`/`ARROWDOWN`/`ARROWUP` could be silently ignored for seconds after entering Tab view, e.g. `ADDRESSBAR <url>` then `ENTER` 3 s after the click didn't navigate. Those commands are dropped while a view transition runs, and a transition only ended inside a drawn frame; with frames stalled on a busy GPU (see the slow-frames entry above), one that finished its 220 ms long ago still counted as running. Confirmed by trace (`transition=true` when the ENTER arrived). `handle_debug_command` now ends a transition whose time is up before handling any command, and a dropped key command is logged (`debug: Enter ignored: ...`) instead of vanishing. Checked by removing the per-frame `finish_transition_if_done` call to simulate a stall: ENTER still navigated.
- **Fixed:** a headless `ARROWDOWN`/`ARROWUP` sent before the address bar's suggestions arrived stayed pending past the `ENTER` that navigated, then highlighted a row in the next edit's dropdown. Reproduced with `ARROWUP` + `ENTER` right after an `ADDRESSBAR`: a later plain `ENTER` searched the last suggestion instead of the typed text. `build_tab_view_ui` now takes both flags every frame, whether or not the dropdown is up, the way a real key press disappears. Found in an audit (2026-09-24) of command guards that read state only a drawn frame updates. The other guards were fine: `WAITTABS` counts spawns through `UserEvent`s, the quick switcher's and bookmark-folder rename's state is set and read by commands, `ESCAPE` is consumed in both Tab and image view, and `transition` is handled by the entry above.
- **WebKit tab input (mouse, keyboard)** is wired up via synthetic GDK events, same as Servo/CEF. An earlier attempt at this caused a runaway-CPU event storm and was reverted (see project memory) — the fix was attaching a real `GdkDevice` to each synthetic event (`gdk_event_set_device`), which the first attempt never did. Verified via repeated live keystrokes/clicks with no CPU escalation, and (after the frame-freeze fix below) correct on-screen text — no dropped or doubled characters. Scroll is implemented the same way but not yet cleanly live-verified (test-harness input-injection reliability issues, not a known code problem).
- **Headless testing against WebKit specifically is measurably flakier than the other two engines.** The exact same test script, unmodified, has been observed to succeed and then completely fail (a command's handler never even firing) on back-to-back runs, whenever a concurrent WSL2/Xvfb/GTK process is involved — confirmed directly via temporary tracing, not assumed. Not a deterministic app bug (Servo/CEF headless tests don't show this); budget generous real wall-clock time (10s+ before the first command, several seconds between each subsequent one) for any WebKit headless test, and re-run once before treating a no-effect result as a real regression.
- **Fixed:** an engine-swapped-to-WebKit tab's rendered frame used to go permanently stale after respawn (title/URL kept updating, the visible content never did) — `GtkOffscreenWindow`'s backing surface never actually adopted a post-spawn `Resize` message's size, so the old size-matching gate on sending `FrameReady` never passed even once. Fixed by sending whatever size the captured pixbuf actually is, rather than requiring it to match what was requested. - **Fixed: the CPU-side pixel work the previous entry's own investigation left unaddressed -- `to_thumbnail_rgba`'s channel swap and `downscale_rgba`'s box filter -- turned out to be the actual dominant idle cost, and both are now GPU-side.** Confirmed before writing any code: re-timing the exact same idle test with only the persistent-texture fix applied still showed ~80ms/frame in debug, unchanged, so the two CPU functions (not texture allocation) were the real target. - **Fixed: a Download/Note/Image/Pdf/Json card stayed "hovered" after the pointer left it**: its border stayed bright and its ✕ stayed up until another card was hovered. `draw_graph_card` passed `is_hovered`, which includes last frame's `self.hovered`, to `finish_draggable_node`, which writes `self.hovered` back from it, so it could never clear. That term is what kept the ✕ drawn while the pointer is on it (the ✕ is registered last, so it takes the hover from both card interacts). - **Fixed: `SCREENSHOT` could be silently lost.** `pending_screenshot` holds one path. When frames stalled (surface acquire timing out headless, or a visible window that wasn't being painted), the next `SCREENSHOT` replaced the waiting one, and `QUIT` exited after one redraw even if that redraw never got a surface. Of four screenshots 3 s apart, often only the first and last were written; a trace showed each request arriving while the previous one was still pending. Now the stdin reader blocks on `SCREENSHOT` until the app has saved it (up to 30 s, then it warns and moves on), the same way `WAITTABS` waits for tab spawns, so later commands, `QUIT` included, can't overtake it. A blocked reader exposed an older problem: the driver scripts ran `sleep` in bash while writing the pipe, so during a `WAITTABS` or `SCREENSHOT` wait they kept going, and the lines they buffered then arrived back to back with no gaps. New `SLEEP secs` pauses the reader itself, so pauses stay in order; the drivers now send `sleep N` lines as `SLEEP`, and run a line starting with `!` in bash (not in step with the app). Checked: the same four-screenshot script now writes all four in a visible window, and a six-screenshot headless run that used to lose one writes all six.
- **Replacing the session drops tab spawns still in flight**: importing or loading a session while tabs were still starting (e.g. the first-launch demo's) let those late tabs land in the new scene. When one's id matched an imported tab's (both count from `tab-0`), it replaced that tab and the tab crash-looped. `replace_running_session` now bumps a `session_generation`, and a spawn result from an older generation is dropped, which shuts its engine host down. Headless repro: before the fix, 1 of 2 runs crash-looped; after it, 4 of 4 runs were clean, with no engine processes left over.
