# The trail popup as a miniature graph view

Status: implemented 2026-10-16 in six tasks (shared camera pieces, `trail_cards`/`trail_edges`, the popup scene, right-click menu, keyboard, docs). Refinements while building: the focus-follows pan is `CardPass.pan_target` (set by `draw_graph_card`, applied by the caller with `GraphCamera::pan_to`; `pan_to_card` and `handle_card_tab` are gone, replaced by `GraphCamera::pan_to` and the free `card_tab_step`); `CardPass.carry` is false in the popup so a page is click-only and a drag pans. Choosing "Open as card" from the popup's menu leaves the popup open (accepted; the menu closes itself). Risk results are at the end of "Risks". Originally: draft (owner answers: pannable and zoomable, recentred on every open, keyboard if it falls out of the refactor). Follows `2026-10-16-trail-strip-design.md`, which made the strip and the popup share a layout, an edge style, a background, a menu and the two actions (`trail_pick`, `open_branch_as_card`). What still differs is the machinery around them: the strip's pages are real graph cards (hover, focus, menu key, pan and zoom) and the popup's rows are hand-drawn in a `ScrollArea`.

## Goal

Draw the Back/Forward branch popup with the Graph view's own card drawing, camera and scene, so the two show the same cards the same way, differ only in the frame around them, and change together. The popup's pages become `draw_graph_card` cards on a `Scene` the user pans and zooms; Tab, Enter and Shift+F10 on a page work as they do in the graph.

## What exists (checked 2026-10-16)

- `build_graph_ui` (`graph_ui.rs:410`) does five things: level data, camera, input (keys, rect-select, link gestures, drops), chrome (toolbar, minimap, outline) and drawing. Only the camera and the drawing are written against "a camera rect" rather than "the app's one graph".
- `GraphCamera` (`graph_ui.rs`) is already a struct (`rect`, `zoom_pct`, `tween`, `momentum`, `drag_history`, `frame_restored`) with `advance`, `fill`, `jump_to`, `ease_to`. `App.camera` is the one instance. The world-to-screen pair comes from `App::graph_world_to_screen_transform(outer)`, which reads only `self.camera.rect`.
- Four places read the camera rect for drawing: `draw_graph_card` culls on `self.camera.rect` (`card.rs:1090`); `draw_graph_edges` culls on it; `draw_graph_dot_grid` passes it to the free `paint_dot_grid`; `pan_to_card` eases `self.camera` (called from `draw_graph_card` on gaining focus, from `handle_card_tab` and from `handle_card_digits`).
- `draw_graph_card` is an `App` method but, for a virtual entry, reads only: `interaction.{dragging,hovered,selected}`, `menus.node_menu` (tooltip suppression), `link.connect_drag`, `graph_lod_simplified`, `card_hint` (written), and the entry's source (`paint_body`, `on_menu`, `on_drop`). `virtual_card_click` adds the source's `on_click`. `CardPass` carries the per-pass rest.
- A right-click on a virtual card is not handled by `draw_graph_card`: `handle_rect_select` (`graph_ui.rs:1290`) hit-tests the pointer and calls `source.on_menu`. Only Shift+F10 is inside the card.
- `TrailSource` (`trail_strip.rs`) builds its entries and edges from `trail_strip_tab()` (focused tab, Graph view) and the tab card's rect. `page_sizes` and `page_rects` do the layout.
- The popup (`popups.rs:1276`) draws `NavHistory::tree()` itself: a `ScrollArea` (max 480 x 240), `POPUP_PAGE` 120 x 28 cells, `POPUP_COLUMN_GAP`/`POPUP_ROW_GAP`, per-row `ui.interact`, `row.context_menu`, `scroll_to_rect` on the first open frame (`popup_centres_cursor`).
- `build_trail_menu` runs from `build_graph_popups`, which is Graph view only.

## Decisions

1. **Not a `GraphCanvas` object; four shared pieces.** The earlier estimate assumed a state bundle (camera, hover, drop target) that the popup would instantiate empty. Reading `draw_graph_card` shows it is not needed: the popup and the strip are never on screen together (the carets live in Tab view, the strip in Graph view), so the popup can read the same `App.interaction` the graph does. What is genuinely general is smaller, and is extracted once:
   - `GraphCamera::transform(outer) -> Transform { zoom_scale, translation, inv_zoom }` replaces `App::graph_world_to_screen_transform` (its callers, 10 sites in 4 files: `graph_ui.rs`, `link_gestures.rs`, `debug_control.rs` and the link-gesture tests, are changed; the App method is deleted).
   - `GraphCamera::begin_frame(outer, ctx) -> Transform` does what `build_graph_ui` does before its `Scene`: `advance`, repaint while a tween or momentum runs, `fill`, `zoom_pct`, and returns the transform. `build_graph_ui` calls it.
   - `canvas::show_scene(ui, &mut rect, drag_pan, body)`: the `egui::Scene` call with the graph's zoom range and `DragPanButtons::PRIMARY`; `build_graph_ui` calls it with `drag_pan` off while a link retargets.
   - A `viewport: Rect` on `CardPass`, a parameter of `draw_graph_edges`, and `pan_to_card(&mut GraphCamera, Rect)`: the four camera reads above take the camera they are given. `draw_graph_dot_grid` is deleted; its one caller calls `paint_dot_grid`.
   `build_graph_ui`'s input, chrome and level-data parts stay where they are. Parked: a `Level`/`View` abstraction over those (it would be additive to this change: the camera is already owned per view, and the event types the popup needs are the ones `draw_graph_card` already returns).
2. **The popup draws the strip's cards.** `TrailSource` splits into `trail_cards(app, tab, origin) -> (Vec<CardEntry>, Vec<LevelEdge>)`, the ungated generator (ids, sizes, layout, edges, highlight), and its `VirtualSource` impl, which gates on Graph view and focus, derives `origin` from the tab card, and calls it. The popup calls `trail_cards` with its tab and origin `(0, 0)`. Both views therefore show the same page ids, sizes (`PAGE` 160 x 44, `MIN_PAGE_WIDTH` 56, `COLUMN_GAP`, `ROW_GAP`), labels and edges. `POPUP_PAGE`, `POPUP_COLUMN_GAP` and `POPUP_ROW_GAP` are deleted.
3. **The popup body is a `Scene`.** Inside the popup `Area` and its frame: fill `theme::BG` (rounded 4), then `canvas::show_scene` over a fixed-size viewport, whose body does what the graph's does: `paint_dot_grid`, `draw_graph_edges`, then each entry through `virtual_card_click` (`draw_graph_card` plus the source's `on_click`). The page-level `paint_trail_page` keeps one path: its `card` parameter and the non-card branch are deleted (the popup is now a card). The viewport is the cards' bounding box clamped to 160..=480 wide and 60..=240 high, so a short trail is not padded with empty canvas.
4. **Camera: owned by the popup, recentred on every open.** `Menus.trail_canvas: Option<(AnchoredPopup, GraphCamera)>`. On the first frame a popup is open (`popup_centres_cursor`, kept, its doc changed from "scroll" to "recentre") its camera `jump_to`s a rect of the viewport's size at 100% zoom: centred on the whole tree if the tree fits the viewport, otherwise on the cursor page. No state survives a close. The popup advances its camera each frame (`begin_frame`), so keyboard-focus pans ease as in the graph; it has no pan momentum (`track_pan_momentum` stays graph-only).
5. **Gestures are the strip's, through the same functions.**
   - Click: `virtual_card_click` runs the source's `on_click` (`trail_pick`). The popup closes when a page was clicked (`CardOutput.response.clicked()` on any entry), including the cursor page, as today.
   - Right-click: the popup tests `card.response.secondary_clicked()` on each card and calls `source.on_menu(app, entry, pointer)`, the call `handle_rect_select` makes for the strip. `build_trail_menu` is also called from the popup builder, so the menu exists in Tab view. It currently closes the menu unless `trail_strip_tab()` is `Some`, which is never so in Tab view, so that condition becomes "the strip is showing (`trail_strip_tab()`) or a branch popup is open (`menus.open_popup` is `BackBranches`/`ForwardBranches`)", plus the existing "its page is live". While `menus.trail_menu` is set the popup ignores clicks outside it (they belong to the menu), and picking "Open as card" closes both.
   - Drag-out: off. `CardPass` gains `carry: bool`; `draw_graph_card` treats a virtual card as a drag source only when `entry.caps().drag_source && pass.carry`. The graph passes `true`, the popup `false`, so a press on a page in the popup is a click or a pan, never a carry.
   - Hover and tooltip: from `draw_graph_card` (the eased fill, `paint_body`'s URL tooltip). The row `on_hover_text` is deleted.
6. **Keyboard falls out; digits and select do not.** The popup builds `CardPass.order` from its entries (entry order), so `draw_graph_card` gives it focus rings, the focus-follows pan (`pan_to_card(&mut popup camera, rect)`), Enter as click, and Shift+F10 as the menu. `handle_card_tab(ui, order, camera)` takes the camera and a rect lookup and runs for the popup's order; Tab past either end leaves the popup as it leaves the graph's cards. The popup does not take focus when it opens (a mouse open would show a focus ring); a keyboard user Tabs from the chip, which should reach the popup's first page in egui's registration order, unverified: the tests set focus directly, and the gate check below confirms the reach, else it is parked. Not added: digit jumps (`handle_card_digits` refuses while a popup is open and in Tab view; a four-page popup does not need numbers), Space select (a page is not `selectable`), Delete. `show_order` is false in the popup (no badges), so it queues no overlay text.
7. **Overlays.** `draw_graph_card` queues decorations on `deferred_overlays`, painted on the Middle-order `graph_decoration_text` layer, which sits below this Foreground popup. The popup's cards queue none (no `stored_controls`, no carry ghost, no badges, no filter dim: `graph_filter` applies only to the graph's level), and a test asserts the popup's `deferred_overlays` stays empty, so the popup does not need an overlay layer. If a future virtual-card feature queues one, that test is where it surfaces.
8. **Deleted** (nothing else used them): the popup's `ScrollArea`, row loop, per-row `ui.interact` and `context_menu`; `POPUP_PAGE`, `POPUP_COLUMN_GAP`, `POPUP_ROW_GAP`; `draw_graph_dot_grid`; `App::graph_world_to_screen_transform`; `paint_trail_page`'s `card` parameter. `page_menu_items` stays (`build_trail_menu`).
9. **Persistence and observability.** None: the camera is not saved. `TOGGLEPOPUP back|forward` keeps working; the gate's screenshots use it.

## Risks, to settle by the first task's prototype

- `egui::Scene` inside an `Area` inside `popup_frame` with `set_opacity(fade)`: unproven here (the graph's `Scene` fills a `CentralPanel`). The prototype draws one page in this shell and checks, in a test, the cull (a page out of the viewport is not registered), a click, and the fade.
- Layer order: `Scene` paints in its own bare layer at its parent's `Order` (the graph comment at `graph_ui.rs:515` records that a bare layer at `Foreground` draws after, so over, every `Foreground` `Area`). Inside this `Foreground` popup the scene's content would cover `trail_menu` (also a `Foreground` `Area`). The first task checks the menu is visible and clickable over a page; the fallback is to build the trail menu at `Order::Tooltip` when the popup hosts it.
- Ids: `draw_graph_card` uses global ids (`("graph_card", id)`, `("graph_card_hover", id)`); the strip and the popup would share page ids if both were on screen. They cannot be today (Tab view versus Graph view); a test opens the popup with the view forced to Graph and checks no id collision warning is raised, and the spec states the exclusion.
- The popup is a small viewport, so a plain scroll over it zooms (as in the graph) rather than scrolling the page behind. A scroll over the popup must not reach the page behind it; `Area` is above, so it should not, and the first task checks.
- `interaction.hovered` may keep a virtual id when the popup closes mid-hover. The graph clears it on the next frame's non-hover (`still_hovered`); the popup's close frame clears it explicitly if the test finds it stale.
- A drag that starts on a page pans only if the page does not sense drag; with `carry` false the page is click-only, so egui hands the drag to the scene behind it. The first task checks that dragging across a page pans the canvas.

**Results (2026-10-16).** Settled by tests in `trail_nav.rs`: the `Scene`-in-`Area` shell (draw, click; the opacity fade is not asserted), a drag across a page pans and does not carry it, recentring on every opening, the long-trail clamp, the trail changing under an open popup. Settled by the menu tests: the menu opens from a right-click and survives in Tab view, and an outside click closes only the menu. The three remaining risks were then pinned headlessly: the page menu is the topmost layer over the pages (`layer_id_at`), a wheel event over the popup moves its camera, and a stale hover after close was a real bug (fixed: a closed popup clears a trail hover). Also fixed after review: Escape closes an open page menu before the popup, a page menu no host drew is dropped, and an eviction recentres the camera. No screenshots were taken (the plan's temporary gate extension was skipped), so real pixels are unchecked.

## Tests

- Camera: `transform` equals the old function's output for the same rect (property check against the removed formula in the test); `begin_frame` fills and advances.
- Popup draws the strip's entries: same ids and rects as `trail_cards` for the tab, at origin zero.
- Popup shape tests from `trail_nav.rs` kept where they still hold (horizontal bezier edges, accent on the path, dot grid, BG fill, ellipsis, click picks, right-click opens "Open as card", menu click does not close the popup, a click outside closes it), rewritten against the scene; the scroll-position test becomes a recentre test (cursor page centred on first open, not again until reopened).
- Keyboard: Tab from the first page focuses the next in entry order and pans an off-screen page into view; Enter picks; Shift+F10 opens the menu; no digit jump.
- Pan and zoom: a drag across empty canvas moves the camera; scroll zooms within `GRAPH_ZOOM_MIN..=GRAPH_ZOOM_MAX`; a drag on a page also pans (no carry).
- Overlays stay empty; a stale `trail_menu` closes (existing).
- Gate: `ui` tier, with `TOGGLEPOPUP` screenshots of a short trail (padding), a long one (clamped, recentred on the cursor) and a zoomed-out one.

## Review rounds

Round 1 (self, against the code): the earlier plan of a `CanvasState` the popup instantiates empty was dropped, because `draw_graph_card` for a virtual entry needs only `App.interaction` and the popup and strip never coexist; right-click is not in `draw_graph_card` (it is in `handle_rect_select`), so decision 5 adds it for the popup; `build_trail_menu` is Graph-view-only, so the popup builder calls it; the Middle-order overlay layer is below a Foreground popup, so decision 7 requires and tests an empty overlay list instead of building a layer. Round 2 (against the code): `build_trail_menu` closes unless `trail_strip_tab()` is `Some` (Graph view only), so decision 5 now widens that condition (it would otherwise have closed the popup's menu in the frame it opened); corrected the call-site count (10 in 4 files, not 12 in 5); confirmed `live_page` needs no view or focus (only the tab's epoch), so the popup's `on_click` works in Tab view; confirmed `handle_card_digits` already refuses in Tab view and with a popup open (decision 6). Not settled by reading: egui 0.36's drag routing past a click-only widget (its source is not unpacked here), so it stays a first-task check, with the fallback of making pages `Sense::click_and_drag` in the popup and ignoring the drag. Round 3 (adversarial, against egui's layering): found that `Scene`'s bare layer would draw over the Foreground `trail_menu` (new risk, with a fallback) and that keyboard entry into the popup was unproven (decision 6 now says so and how it is checked). Round 4 (re-read every decision against the two rounds): no contradictions; one fix, the plan note's review model (400 lines is over the Sonnet threshold, so Opus). A full pass found nothing further material, so the remaining unknowns are the six risks above, all tested in the first task.
