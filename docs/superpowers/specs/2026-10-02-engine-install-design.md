# On-demand engine install (CEF) — design

Status: built 2026-10-02 (plan `docs/superpowers/plans/2026-10-02-engine-install.md`); the README's "On-demand CEF install" entry describes what shipped. Survey and decisions came from a brainstorm.

## Goal

A packaged build ships `manifold`, `manifold-engine-webview2` and the small `manifold-engine-cef` host (about 1 MB), and downloads CEF's runtime (about 172 MB compressed, 423 MB unpacked, measured: `Release/` + `Resources/` of the `minimal` archive) only when a user picks CEF. Engine availability is always visible and explicit: no engine is ever silently missing, silently installing, or silently substituted.

## Scope

- CEF only, Windows first (other platforms: see "Platforms"). Servo stays bundled (decided). WebView2 is the default and always present. WebKit is unchanged (WSL/macOS-native).
- Out of scope: installer integration, a package-manager add-on, delta updates, a hosted manifest or mirror.
- **Product decision (2026-10-02): packaged builds offer CEF on demand, opt-in.** A package ships the 1 MB host and the pin; the runtime downloads only after the user confirms, and CEF is never the default engine. The picker and Settings label it as an optional download. Every release re-pins (the `Cargo.lock` test fails until it does). Bundling the runtime was rejected (423 MB to 1.5 GB per package, and it ties our update cadence to CEF's); shipping no CEF was rejected because Linux and macOS would be left with Servo alone. No packaging pipeline exists in the repo yet, so this binds the first one.

## Decisions (and the alternatives dropped)

- **Source: CEF's own CDN, pinned in the app.** `https://cef-builds.spotifycdn.com/index.json` lists every build with size and SHA-1; the `minimal` archive for CEF 152.0.6 is `…_windows64_minimal.tar.bz2` (171.6 MB; verified 2026-10-02 to answer ranged GETs). Hosting nothing beats a hosted manifest (needs a signing key, and the exact `cef` crate pin means no independent bumps anyway) and a full mirror (re-upload per bump). A GitHub Release mirror is the fallback only if the CDN proves to prune builds.
- **Trust anchor: our own SHA-256, compiled into `manifold`.** SHA-1 from the index is checked too but is not the anchor. A compromised CDN would have to match a hash that ships in the signed app.
- **Bring-your-own runtime** is also supported (a "CEF directory" setting), validated against the pin.

## 1. Pin

A table in the app: CEF version string, archive URL, size, SHA-1, SHA-256. A release script (`scripts/cef-pin.sh`) reads `index.json`, downloads the archive once, computes the SHA-256, and writes the table. A test fails when the pinned version differs from the `cef` crate's CEF version, so a crate bump cannot ship with a stale pin.

## 2. Engine states, always shown

Each engine is in exactly one state, computed in one place (`engine_availability(kind)`), and every place that lists engines shows it:

| State | Meaning | Shown as |
|---|---|---|
| **Installed** | present and matching the app's pin (bundled engines always) | no extra marker beyond the name |
| **Not installed** | needs the download | "Not installed · 172 MB" with a Download button |
| **Installing** | download or unpack in progress | progress bar with bytes; Cancel is in Settings, Engines only (the cards and pickers show the state line) |
| **Update needed** | installed for an older pin (after an app update) | "Update needed · 172 MB" with an Update button |
| **Failed** | last install failed | the reason and a Retry button |
| **Custom** | using a user-chosen CEF directory | the path, with its validation result |
| **Unavailable** | this OS cannot run the engine (see "Platforms") | dimmed (weak text) with "Unavailable: <reason>" on the state line |

**Unavailable is explain-only.** An unavailable engine is dimmed wherever it is listed (picker cards, the Settings default-engine row and Engines section, the opener buttons) and shows its reason. In a picker it has no pointer cursor, is skipped by keyboard focus and arrows, and clicking it does not switch and does not close the picker: it toasts "<engine> is unavailable: <reason>". (The click must stay live, so `add_enabled` is not used: it would swallow it.) A tab that needs it (restored session, new tab from a saved default) is never silently moved to another engine: it fails with the same reason, as the existing failed card for a restored tab, or the spawn-error banner for a new one.

Where it appears: the Settings default-engine picker, the Settings Current Tab picker, the Tab-view Split picker (all three share `build_anchored_engine_picker`), the engine cards in `engine_info.rs` (a state line under each name), and the Settings page's own "Engines" section (installed size, Remove). An engine that isn't Installed is still selectable; choosing it starts the install flow (below), never a silent no-op or a silent fallback to another engine.

A tab, session or restored node that needs a missing engine shows its card as "CEF not installed" with a Download button (the existing failed-tab card with Retry/Open in Default Engine already has this shape), not a generic spawn error.

## 3. Install flow

1. Trigger: choosing the engine, or the card's Download button, or opening a session that uses it. Always preceded by a confirm that states the size ("Download CEF, 172 MB?"), because it is a large network action.
2. Download to `engine-hosts/cef-runtime.part` with HTTP Range resume; progress shown as in section 2 (reusing the download-card UI).
3. Verify SHA-256 (and SHA-1) of the archive before unpacking anything.
4. Unpack only `Release/` and `Resources/` (bz2 + tar) into a temp directory next to the final one; drop build leftovers (`include/`, `cmake/`, `libcef_dll/`, `libcef.lib`, `CMakeLists.txt`, `debug.log`); write a `ready` marker holding the pin; rename the directory into place.
5. Failure at any step removes the temp directory and sets state Failed. The `.part` is deleted only when the archive is bad (hash mismatch, or a corrupt bz2/tar), so a retry downloads afresh; a network error, an idle timeout, a cancel or a file error (disk full) keeps it for resuming. Downloads fail with a network error after 30 s with no data. The state carries the reason, and the failure leaves any previous install untouched.
6. Cancel (Settings, Engines) is seen while downloading (within about 100 ms, even on a stalled read), between unpack entries and before the swap; it removes the temp directory, keeps `.part` and leaves the previous install alone. A new install of that engine waits (a toast says so) until the old thread is done. Install also refuses to start while a CEF tab is live: its process holds the runtime's DLLs open and the swap would fail.

## 4. Lookup

`engine_binary_path` (`process_manager.rs`) keeps its sibling-then-`engine-hosts/` order. The CEF host exe ships with the app; the runtime is resolved from the data directory, and only when the `ready` marker matches the pin. A stale or missing marker yields state Not installed or Update needed, never a spawn that crashes. The downloaded runtime holds no host exe (the archive has none), so at spawn the shipped host is copied into the runtime directory (`ensure_host_copy`): Windows resolves `libcef.dll` from the exe's own directory first. Linux's loader does not, so the host is linked with an rpath of `$ORIGIN` (`manifold-engine-cef/build.rs`), which makes the same copy work there (see "Platforms").

## 5. Management

Settings shows installed size per downloaded engine and a Remove button (deletes the marker first, then `cef-runtime/`, then any `.part`, `.tmp` and `.old` leftovers). When only leftovers exist (no runtime) the button reads "Clear leftovers". An app update that changes the pin turns the state to Update needed, and a stale marker means a spawn is refused: the shipped host links the pinned CEF exactly, so an older runtime would crash it. (This replaces the earlier idea that the old runtime keeps working until the user updates.) The Update button runs the normal install flow. A current runtime outranks a recorded Failed (so the lists agree with what a spawn does); Failed outranks Not installed and Update needed, so a failed update over an old runtime reads Failed, with Retry and Remove.

## 6. Bring-your-own

A "CEF directory" setting accepts a runtime directory. Validation requires the platform's runtime library (`libcef.dll`, `libcef.so` on Linux) and reads the version from one of two sources, the same on every platform: `archive.json`'s `name` field (a runtime exported by the `cef` crate's tool; it wins when present, and an invalid one is refused rather than skipped), else our own `ready` marker (which holds the pin, so a runtime this app installed can be reused as a custom directory). Neither CDN archive (Windows, Linux) carries `archive.json`; a directory with neither source is refused, naming both. Reading the version out of `libcef` itself was skipped: it needs loading the library (`cef_version_info`) or scanning a 285 MB binary. The version is compared against the pin; a match is state Custom, a mismatch shows the found and expected versions and refuses it. A custom directory launches a copy of the host exe placed in that directory (same DLL search order reason as above), refreshed when the shipped host changes. The copy is made to a unique temp name and renamed, under a lock; a user's own `manifold-engine-cef.exe` in a custom folder is overwritten only when it differs from the shipped host (size or modification time), and a matching one is left alone even if a running host has it locked. Archive entry names containing `:` are refused when unpacking (drive-relative names and NTFS streams), and so are names containing `\` (a separator on Windows, an ordinary character on Linux; refused everywhere so both platforms agree).

There is no auto-switch: after an install (or choosing a custom directory) the engine becomes available, but no tab, default or setting changes by itself.

## Platforms

Windows is the only supported install target today. The per-OS facts live in one place, `crates/manifold/src/cef_platform.rs` (`CefPlatform`, selected by `cfg`), and the pins are looked up per platform (`cef_pin::pin_for_platform()`, `Some` only where a real pin exists).

**What is Windows-specific** (all in `CefPlatform` unless noted): the CDN platform id `windows64`; the runtime library `libcef.dll` (the check in `validate_custom`, the "Folder with libcef.dll" hint in Settings, the test fixtures, all read from `CefPlatform::runtime_lib`); the host's `.exe` suffix; the unpack rules (flatten `Release/` and `Resources/`, skip `*.lib` import libraries, `include`, `cmake`, `libcef_dll`, `CMakeLists.txt`, `debug.log`); and, not in the table, the host copy (`ensure_host_copy`, `custom_host_path`, `host_home` in `process_manager.rs`), which exists because Windows resolves the host's implicit `libcef.dll` from the exe's own directory before `PATH` (on Linux the same copy works through the host's `$ORIGIN` rpath). The sibling `cef-runtime/` dev layout and `scripts/sync-runtime-deps.sh` are also Windows-shaped.

**Pin table plan.** One pin per CDN platform id, the same `minimal` type and the same `index.json`: `windows64` and `linux64` (both pinned, CEF 152.0.6), `macosx64`, `macosarm64`. `scripts/cef_pin.py --platform <id> <prefix>` replaces one platform's block in `cef_pin.rs` (default `windows64`); a new platform is that command plus its `CefPlatform` entry. Archive sizes differ per platform and the hash is per archive, so each is downloaded once to pin. The linux64 archive is 321.5 MB (sha256 `daf8c2b6...7135bd`, pinned 2026-10-02).

**No pin on a platform (today: macOS only).** CEF reads as Unavailable ("no CEF build for this platform yet"): no Download or Update offer, picking it toasts that it is not available, and starting an install refuses with the same toast. A runtime already on disk (a dev tree's sibling `cef-runtime/`) still reads Installed. A bring-your-own directory is not accepted either, since there is no pin to validate it against. `engine_availability` is covered by a pure test with no pin.

**Linux: pinned; a CEF tab loads pages (WSL2, once the system NSS libraries are installed)** (no signing issue). The linux64 `minimal` archive was listed on 2026-10-02: one top folder (`cef_binary_<version>_linux64_minimal/`) with `Release/` and `Resources/` as on Windows, plus `include/`, `cmake/`, `libcef_dll/`, `bazel/` and loose build files. `Release/` holds `libcef.so`, `libEGL.so`, `libGLESv2.so`, `libvk_swiftshader.so`, `libvulkan.so.1`, `v8_context_snapshot.bin`, `vk_swiftshader_icd.json` and `chrome-sandbox`; `Resources/` holds the `.pak` files, `icudtl.dat` and `locales/`. The archive has no `archive.json` (a bring-your-own directory made by the `cef` crate's export tool has one; section 6 also accepts our `ready` marker, so an installed Linux runtime validates as a custom directory too), no import libraries, and no symlinks. So the `CefPlatform` entry (`libcef.so`, no exe suffix, the same flatten and skip rules) matches the real layout.

Verified: the pin's size, SHA-1 (against the CDN index) and SHA-256 were taken from one real download; `manifold` compiles on Linux (WSL Ubuntu, 2026-10-02: the `windows` crate moved under `cfg(windows)`, `main.rs`'s DPI call and `with_skip_taskbar` gated), and its whole unit suite passes there, including every `engine_install`, `cef_platform` and `process_manager` test against the linux64 `CefPlatform` entry and pin (validation, unpack of synthetic archives, swap, remove, availability). Compiling there found one real difference: a backslash in an archive entry name is a separator on Windows but an ordinary character on Linux, so `target` now refuses any name containing `\` (as it already did `:`), and an archive unpacks or fails the same on both. WebView2 refuses to spawn with "WebView2 is unavailable: needs Windows"; WebKit refuses by name (see "Which engines run where"); engine hosts are not in a kill-on-exit job (said once on stderr).

**Run on Linux (WSL2 Ubuntu 25.10 with WSLg, 2026-10-02).** One download of the linux64 archive (321,503,907 bytes, SHA-256 matched the pin), then:
- *Unpack.* `engine_install::unpack` on the real archive (the ignored test `unpack_a_real_archive`, debug test binary): verify 19.5 to 21.0 s, unpack 157 to 173 s. The machine's CPU was near 100% busy with other jobs, so these are contended; system `tar xjf` of the same archive took 111 s under the same load. Linux is slow because of size, not the code: `libcef.so` is 1,428,358,816 bytes (`libcef.dll` is 285 MB) and the unpacked runtime is about 1.53 GB (14 files, `locales/` with 220 `.pak`, the `ready` marker), against 423 MB on Windows. That is well over the one-minute bar set on Windows; `bzip2-sys` or a release build would cut the decompression time, but the floor is roughly what `tar` takes.
- *File modes.* The tar headers say 0755 for `chrome-sandbox` and the five `.so` files and 0644 for the rest; `unpack` creates every file with the default mode (0644 here). That is enough: shared libraries load without the exec bit (`ld.so` mapped the 0644 `libcef.so`, and `dlopen` of the 0644 `libEGL.so`, `libvk_swiftshader.so` and `libvulkan.so.1` succeeded; the filesystem is not mounted `noexec`), and the only executable that runs, the host, is not from the archive: `ensure_host_copy`'s `fs::copy` keeps the shipped host's 0755. `chrome-sandbox` is used only with the sandbox on and no user namespaces, and then it must be root-owned and setuid (4755), which no unprivileged unpack can produce, so copying header modes would not help it. Unpack therefore does not restore modes.
- *Library path.* Linux's loader never searches the executable's own directory, and the host had no rpath (`readelf -d`: `NEEDED libcef.so`, no `RPATH`/`RUNPATH`), so the host copied beside `libcef.so` failed to start ("libcef.so: cannot open shared object file", exit 127). `LD_LIBRARY_PATH=<runtime dir>` made it resolve. The host is now linked with `-Wl,-rpath,$ORIGIN` (`manifold-engine-cef/build.rs`, Linux only; the binary carries `RUNPATH [$ORIGIN]`), and the copy in the runtime directory resolves that directory's `libcef.so` with no environment set (`ldd`). An rpath was chosen over `LD_LIBRARY_PATH` at spawn because it keeps the Windows design (the host copy decides which runtime loads) and does not leak into processes the host starts. `RUNPATH` covers the host's direct dependencies only; `libcef.so` is one, and its own dependencies come from the system.
- *System libraries.* `libcef.so` also needs NSS (`libnss3.so`, `libnssutil3.so`, `libsmime3.so`, `libnspr4.so`: Ubuntu packages `libnss3` and `libnspr4`), which this WSL did not have; every other library it needs was present (GTK, X11, ALSA, CUPS and so on, installed earlier for other work). Installed later (`apt-get install libnss3`, which pulled `libnspr4`: 1.6 MB downloaded, 4.6 MB on disk, Ubuntu `2:3.114-1ubuntu0.2`), after which `ldd` finds every library of the host and of `libcef.so`. Most desktops likely have NSS already (Chromium and Firefox packages depend on it; not checked on a clean machine), a minimal install may not, and the download cannot supply it.
- *The app.* `manifold` (debug) runs under WSLg with `--headless` and an isolated profile (`APPDATA`, `XDG_DATA_HOME`, `TMPDIR` set): with the unpacked runtime at `$XDG_DATA_HOME/manifold/engine-hosts/cef-runtime` (Ready by its marker) and CEF as the default engine, a new tab copied the shipped host into the runtime (mode 0755 kept) and launched it from there. Before NSS was installed the host died loading it, and the tab only said "timed out after 10s waiting for engine-host to connect"; see *Start-up failures*.
- *Page load (2026-10-02, with NSS).* Driven through the debug command channel (`--headless`, a seeded CEF tab, `GRAPHOPEN`, `CLICK`, `KEYPAGE`, `TYPE`, `QUIT`) against a local page that reports its `load`, `mousedown` and `keydown` to its server: the page loaded (user agent Chrome/152), the click and the key reached it, the card showed the title the page set after the key and the URL, and the screenshots showed its frames, including the colour change the click made. The click was missed once in 9 such runs (sandbox on); `TYPE` sends characters only, so the page sees no `keydown` for them. Three Linux-only faults had to be fixed first: (1) CEF's initialize failed, "ContentMainRun failed with exit code 28": `CHROME_RESULT_CODE_EULA_REFUSED`, since Chromium 151 requires a first-run EULA on Linux; the host now passes `--no-first-run` (the same failure is reported as tauri-apps/tauri#15979). (2) `manifold` died with SIGBUS in `upload_frame`: on resize the host truncated and regrew the shared frame buffer file under manifold's mapping, which Windows refuses (error 1224) and Linux allows; `SharedFrameBuffer::create` now builds the new buffer in a temp file and renames it over the path on Unix. (3) `manifold` exited with SIGSEGV (139) on every `QUIT` under WSLg, CEF tab or not: smithay-clipboard's worker released its `wl_keyboard` on a Wayland connection that `run_app` had already closed with the event loop (gdb); `App::exiting` now drops egui's state, the GPU state and the window while the loop lives (5 of 5 quits exit 0). Not from the Linux gating: before this round's gating commit `manifold` did not compile on Linux at all.
- *Processes.* Per CEF tab: the host's browser process, two zygotes, a GPU process (a zygote child), a network utility process and one or more renderers. After `QUIT` none was left (checked 3 s later with `ps`, every run). `EngineTab`'s drop sends `Shutdown` then kills the host at once; CEF's children exit on their own. After `kill -9` of the host's browser process with manifold running, its children were gone within 5 s and manifold restarted the tab with a new host ("engine-host crashed ... restarting"). So Linux needs no Job Object equivalent for this. Left behind in `$TMPDIR` per tab: the per-tab log, the frame buffer file (`manifold-frame-<id>.bin`) and Chromium's `org.chromium.Chromium.*` singleton directory; CEF also created an empty `extensions/` directory inside the runtime directory.
- *Start-up failures.* A host that exits before connecting is now reported at once, on every platform, with its exit code and the last lines of its log (`process_manager::connect_host`), e.g. with `libcef.so` hidden: "engine-host exited with code 127 before connecting: .../manifold-engine-cef: error while loading shared libraries: libcef.so: cannot open shared object file: No such file or directory", about 2 s after start instead of 10. A host still running at the timeout reads "engine-host is still running but did not connect within 10s (log: <path>)".
- *A visible window under WSLg.* With `--debug-commands` (a real window) WSLg's own compositor (Weston) crashed with SIGSEGV in about two of three runs, before or after the quit fix alike, and manifold then exited with "Broken pipe" on its Wayland connection (`/mnt/wslg/stderr.log`: weston "terminated with signal 11"). Not investigated further; headless runs never hit it.
- *Building the host.* `manifold-engine-cef` builds for Linux once its Windows Job Object is `cfg(windows)` (the `windows` dependency moved to `[target.'cfg(windows)'.dependencies]`; on Windows nothing changed). `cef-dll-sys` on Linux links `libcef.so` directly (no `libcef_dll_wrapper` build) and needs `include/cef_api_versions.h`, an `archive.json` and the runtime files; without `CEF_PATH` its build script downloads the 321 MB archive itself. A directory with the archive's `include/`, an `archive.json` (`name` of the pinned archive) and links to an unpacked runtime, passed as `CEF_PATH`, builds without a download; the build copies the runtime beside the host in `target/<profile>/`.
- *Sandbox.* Tried on 2026-10-02 with a test build (the `no-sandbox` switch dropped and `no_sandbox: false`; not committed): the page loaded, input reached it and `QUIT` was clean, and the renderers ran in their own user and PID namespaces with a seccomp filter (`/proc/<pid>/status` `Seccomp: 2`), while `chrome-sandbox` stayed an ordinary 0644 file: the namespace sandbox needed no setuid helper. In this WSL user namespaces are unrestricted (`unshare -U` works, `user.max_user_namespaces` 123915, AppArmor is not enabled: `/sys/module/apparmor/parameters/enabled` is `N`, and there is no `kernel.apparmor_restrict_unprivileged_userns`). The host hard-codes `no_sandbox` (its comment says the `sandbox` cargo feature is off, but `Cargo.toml` turns it on; the comment is stale). On Linux, Chromium's sandbox first tries unprivileged user namespaces and falls back to the setuid `chrome-sandbox`. This WSL allows them (`unshare -Ur` works, no AppArmor), but Ubuntu 23.10 and later desktops are documented to restrict them through AppArmor by default (not checked here), which would leave only the setuid helper: a root step at install time, or an AppArmor profile. **Decision (2026-10-02): the sandbox stays off, on Linux and Windows alike.** The host disables it on every platform today, so Linux matches Windows; turning it on for Linux alone would be a new, untested security posture (AppArmor-restricted namespaces are unchecked) with no parity on Windows. Enabling it is its own future task, with per-platform work (Linux: namespaces or the setuid helper; Windows: the sandbox's separate build setup).

- *Install through the app's own download (2026-10-02, WSL2, debug build, fresh `XDG_DATA_HOME`, headless `INSTALLENGINE cef` and `ENGINESTATE cef`).* The real 321 MB archive downloaded, verified and unpacked into `engine-hosts/cef-runtime` under `nice 10` (the unpack alone took about 170 s); state went Not installed, Installing 0..100%, Installed; `ready` held `152.0.6+g708dc14+chromium-152.0.7977.83`, no `.part` or `.tmp` was left, and the directory was 1.5 GB. A CEF tab then spawned (the shipped host was copied beside the runtime), loaded a local page in about 2 s and quit cleanly. `INSTALLENGINE` is refused while a tab is still spawning, so the script waited for the start-up tab first.

- *Platform survey (2026-10-02, read-only).* Linux needs nothing further from this feature. The control channel is `interprocess` (Unix sockets off Windows) and frames are file-backed with `cfg(unix)` paths; both ran in the Linux page-load test. Windows-only calls all have non-Windows fallbacks: the dark title bar (`theme.rs`, no-op), the OLE drag cursor point (`event_loop.rs`, falls back to the last pointer point), DPI awareness and `with_skip_taskbar` (gated). One behaviour was Windows-only: Open Containing Folder (`reveal_in_explorer`, `main.rs`) answers "not supported on this platform yet" elsewhere (an `xdg-open` of the parent folder would fix it). (Open Containing Folder now opens the parent folder with `xdg-open`, or `open` on macOS.) The engine hosts have no job object off Windows, but a deliberate `kill -9` of manifold with a live CEF tab left no CEF process after 1 s (WSL2, 2026-10-02): the host exits when its socket drops, so no `PR_SET_PDEATHSIG` is needed.

Not verified on Linux: scrolling, a real desktop rather than WSLg, the sandbox where AppArmor restricts user namespaces (Ubuntu 23.10 and later desktops). `libvk_swiftshader.so`, `libvulkan.so.1` and `vk_swiftshader_icd.json` ride along in the flattened directory; whether CEF finds them there is unchecked (under WSLg its GPU process reported no DRM device and pages still drew).

**Recommendation (not built): an NSS preflight.** On Linux, before offering the 321 MB download (and again before a spawn), check that the dynamic loader can resolve `libnss3.so`, `libnssutil3.so`, `libsmime3.so` and `libnspr4.so` (`dlopen` each, or read `ldconfig -p`), and if not, show CEF as Unavailable with the reason and the package to install ("needs the system NSS libraries: install libnss3"). That turns a download that cannot work into a one-line instruction. A fuller check would `ldd` the unpacked `libcef.so` after install and list every "not found"; the start-up error above already names the first missing library if one slips through.

**macOS later, and only with a Mac to test on.** CEF there is a framework (`Chromium Embedded Framework.framework`) inside an app bundle, with separate helper executables (renderer, GPU, plugin) that must sit at fixed bundle paths, so the flatten-into-one-directory unpack does not apply. Code signing and notarization matter: whether Gatekeeper accepts a downloaded, unsigned framework next to a signed host is unverified and needs a real test; it may force the `signed` archive or a different distribution altogether. Both `macosx64` and `macosarm64` would need pins. Not started.

**Which engines run where** (`platform_unavailable_reason(os, kind)` in `process_manager.rs`, the one source for availability and the spawn refusal; tested for every OS from any host): Servo everywhere; CEF per its pin; WebView2 Unavailable "needs Windows" off Windows; WebKit available on Windows (through WSL, which is not probed) and Linux, Unavailable "needs Windows or Linux" elsewhere (macOS native WebKit is not wired). Note that on Linux WebKit counts as available but its only host is the WSL-hosted one, launched through `wsl.exe`; until a native Linux launch is wired, a spawn there is refused by name ("WebKit can't start yet: a native Linux WebKit host is not wired up", `webkit_host_missing`) rather than failing on a missing `wsl.exe`. Marking it Unavailable on Linux instead would be one line in `platform_unavailable_reason`, but would hide that the host itself already builds there.

**Platform default.** A profile with no saved choice starts new tabs in the first engine of WebView2, Servo that the OS can run (`platform_default_engine`): WebView2 on Windows (unchanged), Servo elsewhere. CEF is never the default and WebKit needs setup. A `settings.json` without the field takes this default; a saved engine that is Unavailable here is kept as is (never replaced), Settings shows its Unavailable state on the default-engine row, and new tabs with it fail with the reason.

**Re-pin burden.** The shipped host links one CEF build exactly, so every `cef` crate bump re-pins every pinned platform (one download each). The release checklist (README, "Branches") carries that line.

**Product position.** CEF is offered as an opt-in advanced engine, never the default. WebView2 stays the Windows default, and where nothing comparable ships with the OS the defaults are decided separately. Re-pinning is part of the release checklist, not left to whoever notices the test fail.

## Testing

The download-and-verify unit takes its URL from the pin, so tests point it at a local HTTP server (like `scripts/probe_server.py`): resume after a cut connection, a wrong hash rejected, no partially unpacked directory ever visible at the final path, a stale marker reported as Update needed, a custom directory accepted and refused. `engine_availability` is a pure function over the filesystem state and the pin, unit-tested per state. `scripts/chrome-shots.sh` gains views for each state in the picker and the Settings Engines section.

## Open questions

- **Runtime size (measured 2026-10-02, resolved).** The unpacked `minimal` archive's `Release/` + `Resources/` is 423,265,193 bytes (about 404 MiB), of which `libcef.dll` is 284,865,024; it is the same files for a debug or a release host, since the runtime is CEF's own release binary and only the 1 MB host differs. ## System-library preflight (2026-10-02)

CEF on Linux needs `libnss3` and `libnspr4` from the system. `CefPlatform::system_libs` lists them (empty on Windows).
`missing_system_libs()` reads `ldconfig -p` (cached 10 s) and the Download confirm dialog adds a "Missing system
libraries: ..." line before the 321 MB download. It is a warning, not a block: if `ldconfig` cannot be run, nothing is
shown, since unknown is not missing. Checked in WSL with a stub `ldconfig` that omits `libnspr4.so`: it reports exactly that one; real `ldconfig` reports none. The dialog text is unit-tested; the rendered dialog was not viewed.
